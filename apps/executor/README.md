# apps/executor — заготовка (кода пока нет)

## Что это

`executor` — **отдельный процесс/сервис, который будет работать вне Docker,
прямо в Windows-сессии пользователя**. Это «руки» агента на конкретной машине.

Он нужен именно отдельным процессом, потому что автоматизация десктопа
принципиально не запускается в контейнере:

- **COM / win32com** (Word, Excel, Outlook, 1С и прочие Windows-приложения) —
  требует нативной Windows и интерактивной пользовательской сессии;
- **Playwright с реальным профилем браузера** — нужен доступ к профилю
  пользователя, его кукам и уже открытым сессиям;
- **клавиатура/мышь/окна/скриншоты** — нужен доступ к рабочему столу.

## Как будет общаться с `api` и `worker`

Планируемый транспорт (выбор зафиксируем при реализации):

1. **Redis pub/sub** (основной вариант) — `api`/`worker` публикуют команду в
   канал вида `overseer:executor:cmd`, executor слушает канал, выполняет
   действие и отвечает в `overseer:executor:result:<request_id>`.
   Плюс: executor сам инициирует соединение — не нужен входящий порт на
   машине пользователя и проброс через NAT/файрвол.
2. **HTTP** — executor поднимает локальный HTTP-сервер, `api` ходит в него
   напрямую. Проще отлаживать, но требует сетевой доступности машины.

```
[api / worker]  --(команда)-->  Redis  --(подписка)-->  [executor @ Windows]
      ^                                                        |
      |                       (результат)                      |
      +--------------------------------------------------------+
```

## Статус

Пустой пакет. Никакой логики здесь пока нет и намеренно не пишется —
это отдельная задача. В Docker-сборку и `docker-compose.yml` executor
не входит.
