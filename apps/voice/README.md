# apps/voice — голосовой клиент

## Что это

`voice` — **отдельный локальный процесс на машине пользователя, вне Docker**: он слушает
микрофон, распознаёт речь, отправляет её агенту и проговаривает ответ. Отдельным процессом
он нужен по той же причине, что и `executor`, — доступ к железу, которого в контейнере нет:
микрофон и динамики.

Отличие от `executor` — **кроссплатформенность обязательна с первого дня**: разработка идёт
на macOS, целевой деплой — Windows. Поэтому Windows-only зависимости сюда не попадают.

## Он ничего не добавляет на бэкенде

`voice` — это ещё один клиент существующего WebSocket-эндпоинта **`/ws/chat`** (OVE-18),
с тем же конвертом, что и любой другой клиент:

```text
клиент → сервер   {"type": "message", "payload": {"content": "..."}}
сервер → клиент   {"type": "reply",   "payload": {"role": "assistant", "content": "..."}}
сервер → клиент   {"type": "error",   "payload": {"error": "...", "detail": "...", "code": 503}}
```

Схемы конвертов берутся из `libs/schemas/ws.py` — теми же классами, что использует сервер;
локальных копий JSON-формы здесь быть не должно.

## Поток данных

```text
[микрофон] → capture.py → listener.py (wake word + vad.py: нарезка реплики)
    → pipeline.py (stt.py → фильтры) → очередь текста
    → ws_client.py ⇄ /ws/chat (OVE-48)
    → pipeline.py: VoiceSpeaker → tts.py → playback.py → [динамик]
```

Оба конца сомкнуты в OVE-48: `ws_client.py` читает очередь готового текста, отправляет его
`message`-конвертом в `/ws/chat` и отдаёт пришедший `reply` тому же `VoiceSpeaker.speak()`.
`speak()` при этом остаётся прежним — он берёт **любую** строку, не обязательно ответ
ассистента, поэтому `python -m apps.voice.main say "..."` работает как раньше.

## Модель потоков

- callback PortAudio (поток `sounddevice`) — только копирует кадр в ограниченную очередь,
  пометив его текущим `generation` состояния;
- один рабочий поток (строго один: `start()` на ещё живом потоке падает с `RuntimeError`) —
  wake word в состоянии `idle` и накопление реплики в `listening`; кадр с чужим
  `generation` не доходит ни до детектора, ни в реплику;
- главный поток — `asyncio`: STT, фильтры, WebSocket, TTS, воспроизведение.

Через границу поток → цикл едут готовые объекты, а не кадры (`loop.call_soon_threadsafe`):
`WakeWordEvent` и `Utterance`. Обоснование — в
[.claude/knowledge/architecture.md](../../.claude/knowledge/architecture.md), раздел
«`apps/voice` — голосовой клиент (OVE-44)».

## Аудио

Библиотека — **`sounddevice`** (PortAudio через CFFI): колёса с вшитым PortAudio под macOS
и Windows, включая Windows ARM64, ставится без системных зависимостей. Формат внутри
конвейера — **16 kHz, моно, int16**. Тяжёлые движки живут в той же группе зависимостей
`voice` и импортируются лениво, внутри `__init__` своих классов
(`OpenWakeWordDetector`, `FasterWhisperSTT`, `BeepCue`), — сами модули `wake_word.py`,
`stt.py` и `cues.py` в CI импортируются без них. То же и в OVE-47: `SileroTTS`
импортирует `torch` внутри `__init__`, `SoundDeviceSink` — `sounddevice`, поэтому сами
`tts.py` и `playback.py` остаются CI-safe, а вся логика воспроизведения (`SpeechPlayer`)
тестируется через фейковый `AudioSink`.

Под Linux колеса с PortAudio нет — нужен системный `libportaudio2`, без него
`import sounddevice` падает. Поэтому `sounddevice` импортируется **только** в `capture.py`
и `playback.py`, а `apps/voice/__init__.py` остаётся пустым: остальные модули обязаны
импортироваться и тестироваться в CI на `ubuntu-latest` без звуковой карты.

## Wake word (OVE-45)

Движок — [openWakeWord](https://github.com/dscripka/openWakeWord): код под Apache-2.0,
инференс через `onnxruntime`, вход — 16 kHz моно int16 кадрами по 80 мс. Обоснование
выбора и **лицензионная оговорка** (готовые модели фраз идут под некоммерческой
CC BY-NC-SA 4.0 и до поставки наружу обязаны смениться на свою) —
в [.claude/knowledge/architecture.md](../../.claude/knowledge/architecture.md), раздел
«Движок wake word — openWakeWord (OVE-45)».

Фраза берётся из `VoiceSettings.wake_word_phrase` (`VOICE_WAKE_WORD_PHRASE`), дефолт —
`hey jarvis`. Готовые фразы: `alexa`, `hey mycroft`, `hey jarvis`, `hey rhasspy`, `timer`,
`weather`. Модели на «overseer» не существует — она обучается пайплайном openWakeWord и
подключается через `VOICE_WAKE_WORD_MODEL_PATH` (тогда `VOICE_WAKE_WORD_PHRASE` остаётся
меткой для логов).

### Настройки

| Ключ | Дефолт | Смысл |
|---|---|---|
| `VOICE_WAKE_WORD_PHRASE` | `hey jarvis` | фраза активации |
| `VOICE_WAKE_WORD_MODEL_PATH` | пусто | путь к своей `.onnx`-модели вместо готовой |
| `VOICE_WAKE_WORD_THRESHOLD` | `0.5` | порог: ниже — больше ложных срабатываний, выше — чаще не слышит |
| `VOICE_INPUT_DEVICE` | пусто | индекс или часть имени устройства ввода |
| `VOICE_LOG_LEVEL` | `INFO` | уровень логов голосового клиента |

Порог — единственная ручка чувствительности; калибруется по месту. Ориентир с замеров на
синтезированной речи: сама фраза даёт 0.99+, постороннее предложение со словом «Jarvis»
внутри — 0.2, обычная речь — 0.0.

## Реплика и распознавание (OVE-46)

После wake word рабочий поток копит кадры, пока `Endpointer` (`vad.py`) не решит, что
человек замолчал: RMS кадра против одного порога, конец реплики — по паузе, а не по
фиксированной длительности. Готовая реплика уезжает в `asyncio`, там её распознаёт
**faster-whisper** (`stt.py`), а `pipeline.py` решает, годится ли результат для отправки.

VAD намеренно простой: искать речь в записи не его работа — это уже делает `vad_filter`
внутри faster-whisper, — ему нужно только поймать конец реплики. Обоснование выбора (и
почему нет адаптивной оценки шума) — в
[.claude/knowledge/architecture.md](../../.claude/knowledge/architecture.md), раздел
«Захват реплики, эндпоинтинг и STT (OVE-46)».

Пустой текст, одни знаки препинания или неуверенность самой модели — реплика **не
отправляется**: звучит короткий двойной сигнал «не расслышал» (`cues.py`), клиент
возвращается в `idle`. Это заглушка до настоящего TTS из OVE-47: молчание в ответ на
«hey jarvis» неотличимо от сломанного клиента.

### Настройки STT и VAD

| Ключ | Дефолт | Смысл |
|---|---|---|
| `VOICE_STT_MODEL` | `small` | модель faster-whisper: `tiny`/`base`/`small`/`medium`/`large-v3` или путь |
| `VOICE_STT_DEVICE` | `auto` | устройство инференса CTranslate2: `auto`, `cpu`, `cuda` |
| `VOICE_STT_COMPUTE_TYPE` | `int8` | квантизация: `int8`, `int8_float16`, `float16`, `float32` |
| `VOICE_STT_LANGUAGE` | `ru` | язык распознавания; пусто — автоопределение |
| `VOICE_VAD_SPEECH_RMS` | `300.0` | порог речи по RMS кадра (шкала int16) |
| `VOICE_VAD_SILENCE_S` | `0.8` | пауза, после которой реплика считается законченной |
| `VOICE_VAD_START_TIMEOUT_S` | `3.0` | сколько ждать начала речи после wake word |
| `VOICE_VAD_MAX_UTTERANCE_S` | `30.0` | потолок длины реплики |

`VOICE_VAD_SPEECH_RMS` — единственная ручка калибровки VAD, аналог порога wake word.
Срезает конец фразы или ловит шум вентилятора — крутить её. Ориентир: синтезированная
речь на 16 kHz даёт RMS ~4500, комнатный шум — десятки.

`VOICE_STT_MODEL` — компромисс, а не оптимум. На macOS/CPU с `int8` модель `small`
распознаёт реплику в 1.4 с за ~2.4 с, в 15 с — за ~3 с; `medium` заметно точнее на
русском, но добавляет задержку, которую в диалоге слышно.

Первый запуск скачивает веса модели (`small` — около 460 МБ) в кэш Hugging Face.

### Как запустить

```bash
uv sync --group voice                  # openwakeword, sounddevice, faster-whisper, torch
uv run python -m apps.voice.main
```

Первый запуск скачивает модели (~6 МБ) в `site-packages/openwakeword/resources/models` —
нужен интернет; дальше запускается офлайн. Скажите фразу — в логи уйдёт строка
`voice.wake_word` со скором и `epoch`:

```text
2026-09-03 23:50:22 [info] voice.listening   phrase='hey jarvis' threshold=0.5
2026-09-03 23:50:31 [info] voice.wake_word   phrase='hey jarvis' score=0.87 epoch=1 dropped_frames=0
```

`epoch` в этих строках — номер живого соединения с `/ws/chat`, его ведёт `ws_client.py`
(OVE-48). Запущенный без сервера клиент слушает и распознаёт как обычно, но отправить
реплику ему некуда: `epoch` не совпадёт, и она будет отброшена. После срабатывания скажите
запрос — факт распознавания уйдёт в лог строкой `voice.transcript_ready`:

```text
2026-09-04 17:20:44 [info] voice.wake_word_detected  phrase='hey jarvis' score=0.98 epoch=1
2026-09-04 17:20:47 [info] voice.utterance_captured  duration_s=2.88 outcome=speech truncated=False
2026-09-04 17:20:48 [info] voice.transcript_ready    epoch=1 language=ru duration_s=2.88 chars=22
```

**Самого текста в логах нет и не будет** — ни здесь, ни в `voice.transcript_rejected`:
расшифровка речи пользователя может нести что угодно, а логи живут дольше и под более
слабым доступом, чем база. В лог идут только метаданные: язык, длительность, число
символов и метрики распознавания.

Дальше текст уходит в `/ws/chat` — см. «Клиент `/ws/chat` (OVE-48)» ниже.

### Разрешения ОС на микрофон

- **macOS**: при первом запуске система спросит доступ к микрофону — разрешение
  выдаётся *терминалу* (или IDE), из которого запущен процесс. Отказали — включается в
  «Системные настройки → Конфиденциальность и безопасность → Микрофон».
- **Windows**: «Параметры → Конфиденциальность → Микрофон», должен быть разрешён доступ
  для классических приложений.

Список устройств — `uv run python -c "import sounddevice; print(sounddevice.query_devices())"`;
нужный индекс или кусок имени кладётся в `VOICE_INPUT_DEVICE`.

## Синтез речи и воспроизведение (OVE-47)

`VoiceSpeaker.speak(text)` (`pipeline.py`) — единственная точка озвучки: она переводит
состояние в `speaking`, синтезирует весь текст целиком (`tts.py`), проигрывает его
(`playback.py`) и **в любом исходе** возвращает состояние в `idle`. Пока идёт `speaking`,
wake word выключен (`state.py`) — это и есть защита от эха без AEC: иначе агент услышал бы
собственный ответ и разбудил сам себя.

Движок — [Silero TTS](https://github.com/snakers4/silero-models) (модель `v4_ru`, инференс
на `torch`, CPU). Локальный, как и STT: ключей провайдеров у голосового клиента нет, и
отправлять наружу текст ответа ради синтеза — отдельное решение, а не умолчание.
Обоснование выбора и модель потоков — в
[.claude/knowledge/architecture.md](../../.claude/knowledge/architecture.md), раздел
«Синтез речи и воспроизведение (OVE-47)».

Стриминга нет: `reply` от `/ws/chat` и так приходит целиком (OVE-18), синтезировать по
кусочкам нечего. Silero не берёт больше ~1000 символов за вызов, поэтому длинный текст
режется `split_for_synthesis()` по границам предложений (дальше — по запятым, затем по
словам), а куски склеиваются в одну реплику до начала воспроизведения.

`playback.py` устроен как зеркало `capture.py`, но короче: `SpeechPlayer` — один рабочий
поток (строго один: `start()` на живом потоке падает с `RuntimeError`, как у
`VoiceListener`), который тянет реплики из очереди и пишет их блоками в `AudioSink`.
Блокирующая запись в `sounddevice.OutputStream` живёт в этом потоке, а не в callback'е:
у вывода, в отличие от входа, нет требования «не задержать ни на миллисекунду чужой поток»,
зато есть требование «дождаться конца», и блокирующая запись даёт его бесплатно.

Реплика помечается текущим `generation` состояния при постановке в очередь и сверяется с
актуальным **дважды** — перед началом воспроизведения и перед каждым блоком, — той же
механикой, что и кадры на входе. Сменилось состояние, пока реплика ждала очереди или уже
звучала (пришёл новый ход, клиент остановили) — остаток не доигрывается. `stop()` будит
ждущего вызывающего исходом `interrupted`, а падение устройства прокидывается в `speak()`,
где ловится и возвращает состояние в `idle`, — поток воспроизведения от этого не умирает.

### Настройки TTS

| Ключ | Дефолт | Смысл |
|---|---|---|
| `VOICE_TTS_MODEL_URL` | `https://models.silero.ai/models/tts/ru/v4_ru.pt` | откуда скачать модель, если её нет локально |
| `VOICE_TTS_MODEL_PATH` | пусто | путь к уже скачанной `.pt`; пусто — кэш `~/.cache/overseer/tts` |
| `VOICE_TTS_VOICE` | `xenia` | голос внутри модели: `aidar`, `baya`, `kseniya`, `xenia`, `eugene`, `random` |
| `VOICE_TTS_SAMPLE_RATE` | `24000` | частота синтеза и вывода: `8000`, `24000` или `48000` |
| `VOICE_TTS_DEVICE` | `cpu` | устройство инференса torch |
| `VOICE_OUTPUT_DEVICE` | пусто | индекс или часть имени устройства вывода |

Частота вывода — своя, к конвейерным 16 kHz отношения не имеет: те про вход, где формат
диктуют движки wake word и STT. Неизвестный голос отклоняется при загрузке модели с
перечислением доступных, неподдерживаемая частота — валидатором `VoiceSettings`.

Первый запуск скачивает `v4_ru.pt` (~38 МБ). Синтез фразы в 4 с занимает на macOS/CPU
меньше секунды.

### Как проверить озвучку

```bash
uv run python -m apps.voice.main say "Отчёт за август сформирован."
```

Без аргумента проговаривается фраза по умолчанию. Команда собирает те же компоненты, что и
основной цикл, но без микрофона: синтез → воспроизведение → возврат в `idle`.

## Клиент `/ws/chat` (OVE-48)

`ws_client.py` — единственное место, где голосовой клиент разговаривает с сервером, и
единственный владелец `epoch`. Соединение живёт в `run()`: подключился — отдал ход
`_serve()`, оборвался — подождал и переподключился, и так до остановки процесса. Внутри
соединения одновременно крутятся две петли: отправка (читает очередь `Transcript`) и приём
(читает сокет); падение любой из них закрывает соединение и уводит клиент в реконнект.

**`epoch` растёт на каждой смене состояния соединения** — и на подключении, и на обрыве,
той же механикой, что `generation` в `state.py`. Поэтому «сейчас соединения нет» никогда не
совпадает с epoch какого-нибудь живого сокета, и реплика, записанная в паузе между
попытками, не уедет в новый разговор. Сверок по-прежнему две (OVE-46): первая — в
`pipeline.py` перед постановкой текста в очередь, вторая — здесь, перед самой отправкой в
сокет. Не совпало — реплика молча выбрасывается: это агент, который действует на компьютере
пользователя, и «удали черновик» через три минуты после реконнекта хуже, чем не доехавшее
вовсе.

**Ход не заканчивается на отправке.** `pipeline.py` теперь оставляет состояние в `thinking`,
когда текст ушёл в очередь, — до этого он возвращал `idle`, потому что ответа ждать было не
от кого. Возврат в `idle` (и вместе с ним включение wake word) — обязанность `ws_client.py`:
он делает это после ответа, после ошибки, после дропа устаревшей реплики и после обрыва
соединения. Пока идёт `thinking`, микрофонные кадры отбрасываются, то есть перебить агента
на середине хода нельзя — это та же граница v1, что и отсутствие barge-in.

**Ошибка проговаривается, а не проглатывается.** На `error`-конверт клиент говорит короткую
фразу («Не удалось получить ответ от агента»), а `code`, `error` и `detail` уходят в лог:
молчание в ответ на запрос неотличимо от сломанного клиента. Конверт, пришедший, когда
клиент ничего не спрашивал (например, `404` на неизвестный `conversation_id` сразу после
подключения), только логируется — иначе неверно настроенный id превратился бы в
проговариваемую ошибку на каждой попытке переподключения.

**Реконнект — с экспоненциальной паузой**: `VOICE_WS_RECONNECT_INITIAL_S`, дальше удвоение
до `VOICE_WS_RECONNECT_MAX_S`, счётчик сбрасывается после успешного подключения. Неожиданное
исключение внутри соединения не убивает процесс: оно логируется и приводит к той же паузе и
той же попытке переподключиться.

### Настройки клиента

| Ключ | Дефолт | Смысл |
|---|---|---|
| `VOICE_WS_URL` | `ws://localhost:8000/ws/chat` | адрес `/ws/chat` |
| `VOICE_CONVERSATION_ID` | пусто | диалог; пусто — сервер отдаёт диалог по умолчанию |
| `VOICE_WS_RECONNECT_INITIAL_S` | `1.0` | первая пауза перед переподключением |
| `VOICE_WS_RECONNECT_MAX_S` | `30.0` | потолок паузы |

### Как проверить полный цикл

```bash
docker compose -f docker/docker-compose.yml up -d postgres redis
uv run uvicorn apps.api.main:app --reload      # /ws/chat должен быть в этой сборке
uv run --group voice python -m apps.voice.main
```

Скажите фразу активации, после паузы — запрос; ответ агента прозвучит в динамике. Весь ход
виден в логах одной цепочкой, с общим `epoch`:

```text
voice.ws_connected        epoch=1 url=ws://127.0.0.1:8001/ws/chat
voice.wake_word_detected  phrase='hey jarvis' score=0.798 epoch=1
voice.utterance_captured  duration_s=5.2 epoch=1 outcome=speech
voice.transcript_ready    epoch=1 language=ru chars=36
voice.ws_message_sent     epoch=1 chars=36
voice.ws_reply            epoch=1 role=assistant chars=6
voice.spoken              chars=6 duration_s=0.79 outcome=played
```

Текста в логах по-прежнему нет — ни своего, ни ответа агента: только длины и метаданные.

## Статус

Цикл замкнут: микрофон → wake word → нарезка реплики → faster-whisper → фильтры → `/ws/chat`
→ LLM → `reply` → Silero → динамик, и обратно в `idle` к следующей фразе активации. Не
сделано в v1: стриминг, barge-in, подавление эха, несколько диалогов, голосовое
подтверждение необратимых действий (ждёт конверта из эпика 5). В `docker-compose.yml`
`voice` не входит и входить не должен.
