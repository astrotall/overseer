# Overseer

Системный ИИ-агент, который управляет компьютером пользователя по голосовой или текстовой
команде: LLM через function calling решает, какой инструмент вызвать, а инструменты —
обёртки над реальными приложениями (COM/win32com, Playwright, файловая система, шелл) —
выполняют действие на машине пользователя.

## Расположение кода

Монорепо: `apps/` — то, что запускается (процессы со своей точкой входа), `libs/` — то, что
переиспользуется (общий код без точки входа). Зависимость однонаправленная: `apps/` → `libs/`,
библиотеки никогда не импортируют приложения.

- `apps/api` — FastAPI: роуты, WebSocket, DI-зависимости, lifespan с подключениями к
  PostgreSQL и Redis.
- `apps/worker` — Arq-воркер: фоновые и долгие задачи, цепочки рассуждений, инструменты,
  исполняемые прямо на Python.
- `apps/executor` — **заготовка под Windows-сервис** (COM/win32com, Playwright с профилем
  пользователя, GUI). Пустой пакет, в Docker-сборку не входит. Текущее окружение разработки
  — macOS/Linux + Docker, поэтому код отсюда, скорее всего, **не запустится и не
  оттестируется здесь напрямую**: писать его можно, но не пытайся выполнять или тестировать,
  пока об этом явно не попросили и не подтвердили, что окружение это поддерживает. Детали —
  в `apps/executor/README.md`.
- `libs/core` — конфиг (pydantic-settings), логи (structlog), исключения.
- `libs/db` — SQLAlchemy `Base`, async engine и session, Redis, ORM-модели.
- `libs/llm` — клиенты Anthropic и DeepSeek, провайдер-независимый контракт под tool-calling.
- `libs/tools` — реестр инструментов агента: описание для function calling + исполнитель.
- `libs/schemas` — Pydantic v2 DTO.

## Правила, общие для всего репозитория

- Комментариев в коде не пишем.
- Строгая типизация: type hints везде. В `pyproject.toml` включён `disallow_untyped_defs`,
  так что функция без аннотаций просто не пройдёт `mypy`. Не используй `Any` без
  необходимости и не глуши проверки: `# type: ignore` — только с явной причиной рядом
  (`warn_unused_ignores` тоже включён, лишний ignore будет ошибкой).
- Не создавай абстракции сверх того, что нужно для текущей задачи.
- Перед реализацией ищи существующий паттерн в `libs/` и `apps/` и переиспользуй его — не
  изобретай новый без причины.
- Ветки, сообщения коммитов и пул-реквесты — строго по [CONTRIBUTING.md](CONTRIBUTING.md):
  Conventional Commits, весь текст коммита на английском (документация в репозитории
  остаётся на русском), тип и область по-английски, ключ задачи Jira `OVE-<номер>` в имени
  ветки, футере коммита и заголовке PR. Ключа не знаешь — спроси, не выдумывай номер. Там
  же список файлов, которые обязаны меняться в одном коммите (ORM-модель SQLAlchemy +
  Alembic-миграция, поле `Settings` + `.env.example`, инструмент + его схема) — эти пары
  расходятся молча, поэтому сверяйся с ним перед тем, как предлагать коммит.
