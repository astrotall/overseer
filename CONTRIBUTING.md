# Как работать с репозиторием

Ветки, коммиты и пул-реквесты. Правила общие для всего репозитория — `apps/` и `libs/` живут по одним и тем же, разделения на «фронт» и «бэк» здесь нет: overseer целиком на Python.

## Ветки

`main` — всегда рабочая: в неё не пушим напрямую, только через пул-реквест. Всё остальное — короткоживущие ветки от `main`.

```
<тип>/OVE-<номер>/<краткое-описание-через-дефисы>
```

Тип — тот же, что у коммита (см. ниже). Ключ задачи — заглавными, ровно как в Jira. Описание на латинице, в нижнем регистре, 2–5 слов по сути задачи.

```
feat/OVE-42/tool-registry-skeleton
fix/OVE-118/ws-drops-binary-frames
refactor/OVE-203/split-session-factory
docs/OVE-77/tool-calling-contract
```

Ключ обязателен: по нему Jira сама привязывает ветку, коммиты и пул-реквест к задаче и двигает её статус. Ветка без ключа в задаче не появится — связывать руками потом никто не будет.

Без задачи в Jira ветку заводим только на мелочь, которую не заводят в трекер (`chore/bump-ruff-0-9`, `ci/fix-uv-cache-key`). Всё, что меняет поведение продукта, задачу имеет.

Ветка живёт до мержа и удаляется сразу после. Долгоживущих веток вроде `develop` у нас нет: команда маленькая, ветвление плоское.

## Коммиты — Conventional Commits

```
<тип>(<область>): <описание>

[тело — зачем, если неочевидно]

[футер — breaking changes, ссылки]
```

Заголовок: до ~72 символов, **на английском**, в повелительном наклонении, без точки в конце. Тип и область тоже английские — они часть спецификации, и по ним строится история.

**Язык.** Весь текст коммита — заголовок и тело — на английском. То же для имён веток и заголовков PR. На русском в репозитории остаётся внутренняя документация: `.claude/knowledge/`, этот файл, `CLAUDE.md`, тексты ошибок в коде.

`README.md` — единственное исключение: он ведётся **на английском**. Это осознанное решение, а не недосмотр. README — витрина репозитория: его читают снаружи, до того как решат в него заходить, и он же единственный документ, который видно в поиске по GitHub и в превью ссылки. Остальные файлы — рабочие материалы команды, их читают уже внутри, и русский там дешевле в поддержке. Правило простое: **README — по-английски, вся внутренняя документация — по-русски.** Переводить `.claude/knowledge/`, `CONTRIBUTING.md` и `CLAUDE.md` «за компанию» не нужно.

```
feat(tools): add "write_document" tool spec

OVE-42
```

Ключ задачи — отдельной строкой в футере, через пустую строку после заголовка или тела. В заголовок его не тащим: заголовок читают люди, футер читает Jira.

```
feat(tools): add "write_document" tool spec
fix(api): don't drop binary frames on the ws channel
refactor(db): move the async session factory into libs/db
docs(architecture): document the worker to executor transport
chore(deps): bump anthropic to 0.45
ci: run alembic upgrade head on PRs
```

### Типы

| Тип | Когда |
|---|---|
| `feat` | новая функциональность для пользователя |
| `fix` | исправление бага |
| `refactor` | правка кода без изменения поведения |
| `perf` | оптимизация |
| `style` | форматирование, не влияющее на смысл |
| `docs` | документация, включая `.claude/knowledge/` |
| `test` | тесты |
| `build` | сборка, зависимости, `pyproject.toml` |
| `ci` | пайплайны, git-хуки |
| `chore` | всё остальное, что не попадает в историю изменений продукта |
| `revert` | откат коммита |

### Области

По приложению из `apps/`: `api`, `worker`, `executor`.
По библиотеке из `libs/`: `db`, `llm`, `tools`, `schemas`, `core`.
Общее: `deps`, `ci`, `docs`.

Область необязательна, если правка не привязана к одному месту.

### Ломающие изменения

Восклицательный знак после области и футер:

```
feat(llm)!: rename ToolSpec.input_schema to parameters

BREAKING CHANGE: every tool spec and provider adapter must update together;
there is no compatibility shim on read.
```

## Задачи в Jira

Ключ задачи — `OVE-<номер>`, всегда заглавными: `OVE-42`, не `ove-42` и не `Ove42`. В нижнем регистре Jira его не распознаёт, и связка с задачей молча не сработает.

Где ключ обязан быть — три места, каждое даёт свою связь:

| Где | Зачем |
|---|---|
| Имя ветки | Jira показывает ветку в задаче и предлагает создать PR |
| Футер коммита | коммиты видны в панели разработки задачи |
| Заголовок PR — в конце, в скобках | пул-реквест привязывается к задаче и двигает её статус |

```
feat(tools): add "write_document" tool spec (OVE-42)
```

Статус двигает тот, кто делает задачу, — не ждём, что это сделает кто-то другой на стендапе:

| Когда | Статус |
|---|---|
| Взял в работу, завёл ветку | **In Progress** |
| Открыл пул-реквест | **In Review** |
| PR смержен в `main` | **Done** |
| Ждём ответа заказчика, чужого PR, доступа | **Blocked**, и в комментарии — чего именно ждём |

Одна задача — одна ветка — один PR. Если задача разрослась, дробим её в Jira на подзадачи, а не тащим три несвязанные правки в одну ветку.

Если PR закрывает несколько задач, ключи перечисляются в футере коммита по строке на каждый, а в заголовке PR — через запятую: `(OVE-42, OVE-43)`.

> Названия статусов взяты стандартные. Если на доске колонки называются иначе — поправьте таблицу под реальный воркфлоу, ключ `OVE-` от этого не меняется.

## Что обязано ехать в одном коммите

Есть пары файлов, которые расходятся молча — и это ловится не тестами, а только в рантайме. Их правим вместе:

- **Новый инструмент для LLM** (function calling) → исполнитель и его описание (`ToolSpec`) — вместе, оба в `libs/tools`: по [architecture.md](.claude/knowledge/architecture.md) реестр инструментов — это «описание для function calling + исполнитель», а `libs/llm/base.py` даёт только *тип* `ToolSpec` (`name`, `description`, `input_schema`) и реэкспортит его из `libs/llm/__init__.py`. Отдельного места регистрации в `libs/llm` нет — класть схему туда не нужно. Плюс документация контракта инструментов, когда она появится (отдельный файл в `.claude/knowledge/` по образцу будущего `api-contract.md` — см. там же, раздел «Что ещё не специфицировано»). Оговорка: `libs/tools` сейчас пуст, реестра ещё нет — его форму фиксирует первая задача, которая заведёт инструмент; до тех пор не выдумывай ни имена инструментов, ни способ регистрации.
- **Новая или изменённая SQLAlchemy-модель** → сама правка + импорт модели в `libs/db/models/__init__.py` + Alembic-миграция — всё одним коммитом. Импорт обязателен: `alembic/env.py` делает `from libs.db import models` и берёт `models.Base.metadata`, то есть выполняется только `libs/db/models/__init__.py`. Таблица попадает в `Base.metadata` в момент выполнения `class`-определения, поэтому модуль, который никто не импортировал, для `--autogenerate` не существует — он молча сгенерирует пустую миграцию. Без миграции схема БД разъезжается с кодом (в `alembic/versions/` сейчас нет ни одной ревизии — первая модель приносит и первую миграцию).
- **Новое или переименованное поле `Settings`** (`libs/core/config.py`) → соответствующий ключ в `.env.example` — тем же коммитом. `.env.example` — единственное место, где видно, какие переменные вообще существуют: поле без ключа никто не найдёт, а ключ без поля молча проглотится (`extra="ignore"`). Исключение — `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_PORT`, `REDIS_PORT`: это переменные для docker compose, полей `Settings` под ними нет и быть не должно, правило на них не распространяется.
- **Изменение зависимостей** (`pyproject.toml`: `[project] dependencies` или `[dependency-groups] dev`) → обновлённый `uv.lock` в том же коммите. `uv add` / `uv remove` / `uv lock` делают это сами — достаточно не забыть застейджить лок. Разошлись — и `uv sync --dev` в CI и в хуках поставит не те версии, которые заявлены в манифесте.
- **Новый домен/модуль в `libs/`** → код + контракт границ слоёв. *(TODO: когда добавим import-linter или аналог — до тех пор направление зависимостей `apps/ → libs/` и «`libs/` не импортирует `apps/`» держим руками, см. [architecture.md](.claude/knowledge/architecture.md).)*
- **Решение по открытому архитектурному вопросу** (разделение `api` / `worker` и будущего `executor`, транспорт до `executor`, формат подтверждения необратимых действий, схема памяти агента) → фиксируется явно: в описании PR, а если решение долгоживущее — отдельным файлом в `.claude/knowledge/`. Не оставляем его только в переписке.

## Пул-реквесты

Перед пушем прогони проверки локально — CI гоняет ровно их, и упасть в пайплайне за то, что ловится за секунды на машине, обидно:

```bash
pre-commit run --all-files && pytest
```

`pre-commit run --all-files` прогоняет ruff и mypy по всему дереву; `ruff check --fix` и `ruff format` чинят всё автоисправимое сами.

Заголовок PR — как заголовок коммита плюс ключ задачи в конце: `feat(tools): add "write_document" tool spec (OVE-42)`. В описании: что меняется и зачем.

Описание PR открывается по шаблону [`.github/pull_request_template.md`](.github/pull_request_template.md) — GitHub подставляет его в тело нового PR, дальше заполняешь. Секции: что/зачем, ссылка на задачу, чек-лист проверок. **Строку `Closes https://<ваш-домен>.atlassian.net/browse/OVE-<n>` не удаляй и подставь реальный ключ** — ключ `(OVE-<n>)` в заголовке нужен Jira, а полный URL в теле — CodeRabbit'у, чтобы подтянуть контекст задачи (см. раздел про CodeRabbit ниже). Это две разные связки, обе нужны.

Один PR — одна задача. Рефакторинг соседнего кода «заодно» выносится в отдельный PR: смешанный диф невозможно ревьюить.

## Git-хуки — pre-commit

Те же проверки, что гоняет CI, стоят локально в git-хуках через [pre-commit](https://pre-commit.com) — ошибка ловится за секунды на машине, а не через минуты красным пайплайном. Конфиг — [`.pre-commit-config.yaml`](.pre-commit-config.yaml) в корне.

**Установка.** `pre-commit` — отдельный инструмент, не зависимость проекта: поставь его один раз (`uv tool install pre-commit` или `pipx install pre-commit`). Дальше из свежего клона всё включается одной командой — она ставит хуки всех трёх стадий и подтягивает их зависимости:

```bash
pre-commit install --install-hooks && pre-commit install --hook-type commit-msg --hook-type pre-push
```

Больше из свежего клона ничего не нужно.

Проверки разнесены по стадиям: **быстрое — на каждый коммит, тяжёлое (тесты) — раз перед пушем.** Так коммит не тормозит, а тестовая регрессия ловится до отправки.

**Что гоняет `pre-commit`** (быстро, на каждый коммит):

- `ruff check --fix` — линт с автофиксом (набор правил `E`, `F`, `I`, `UP`, `B`, `ASYNC`, `C4`, `SIM` — см. `pyproject.toml`), **по фактически изменённым (staged) `*.py`**;
- `ruff format` — форматирование, тоже только по staged `*.py`;
- `mypy apps libs` — типы, strict-конфиг из `pyproject.toml`, **по всему дереву целиком**.

Разница между ruff и mypy тут существенная. У ruff-хуков имена staged-файлов идут в командную строку, поэтому проверяется ровно то, что застейджено. У mypy стоит `pass_filenames: false`: имена файлов ему не передаются, он всегда проверяет `apps` и `libs` целиком — независимо от того, что в коммите. Staged-файлы решают у него только одно: запускать хук вообще или нет. Задет хотя бы один `*.py` — mypy пройдёт по всему дереву и может упасть на файле, которого вы не трогали.

Всё — через `uv run`, той же версией инструмента, что зафиксирована в `uv.lock`. Коммит, не задевший `*.py`, эти хуки пропускает.

**Что гоняет `pre-push`** (тяжёлое, раз перед пушем):

- `pytest` — весь набор тестов (`uv run pytest`).

**Что гоняет `commit-msg`** — две проверки сообщения коммита:

- [`conventional-pre-commit`](https://github.com/compilerla/conventional-pre-commit) — формат Conventional Commits **жёстко**: сообщение не того вида коммит отклоняет;
- локальный `scripts/check_task_key.py` — наличие ключа `OVE-<n>` в теле/футере, **только предупреждением**: коммит он не отменяет никогда. Если ключа нет, печатает напоминание — но не для всех сообщений: заголовки, начинающиеся с `chore`, `ci`, `build`, `revert`, `merge` или `bump`, скрипт пропускает молча, без вывода вовсе, чтобы не шуметь на тривиальных правках без задачи (см. выше).

**Обход** — `git commit --no-verify` / `git push --no-verify` (`-n`) пропускают хуки целиком. CI хуки не запускает — он и так гоняет те же проверки напрямую, двойной работы нет.

## Что проверяет CI

Пайплайн [`.github/workflows/ci.yml`](.github/workflows/ci.yml) запускается на каждый PR в `main` и на пуш в `main`. Один job, по шагам:

- **ruff** — `ruff check .` (линт) и `ruff format --check .` (форматирование);
- **mypy** — `mypy apps libs`, strict-конфиг из `pyproject.toml`;
- **alembic** — `alembic upgrade head` на чистой PostgreSQL из сервис-контейнера: миграции обязаны накатываться с нуля;
- **создание тестовой базы** — `psql ... -c 'CREATE DATABASE overseer_test'` на том же сервис-контейнере, между `alembic upgrade head` и тестами: без неё фикстура `db_engine` не поднимется, а под `CI` недоступная база не пропускает тесты, а роняет их;
- **pytest** — весь набор тестов, с покрытием: `pytest --cov --cov-report=term-missing --cov-report=xml`. Отдельным шагом (`if: always()`) `coverage.xml` уезжает артефактом сборки — порога `fail_under` нет, покрытие тут информация, а не гейт.

Красный CI не мержим.

## Автоматическое ревью — CodeRabbit

Поверх линтеров PR, нацеленные на `main`, получают автоматическое ревью от **CodeRabbit** — GitHub App, который читает дифф и ищет то, чего линтеры не видят: логические баги, дублирование, мёртвый код, проблемы безопасности. Черновики (draft PR) пропускаются. Он **дополняет** ruff/mypy, а не повторяет их — конфиг [`.coderabbit.yaml`](.coderabbit.yaml).

- **Где вывод.** Комментарии прямо в PR: общая сводка (walkthrough) и инлайновые замечания на строках. Отдельного шага в GitHub Actions нет — это внешний App, существующий CI он не трогает.
- **Блокирует ли мерж.** Нет. Инструмент **advisory**: `request_changes_workflow: false`, ревью не заводит required-check. Читаем как подсказку, а не как гейт. Промоут в обязательную проверку — отдельное решение, когда сигнал докажет полезность.
- **Стоимость.** Тариф зависит от видимости репозитория (public/private) и может накладывать плавающий rate limit на число ревью в час — уточни в личном кабинете CodeRabbit, не полагайся на умолчания.
- **Язык.** Комментарии ревью — на русском (`language: "ru-RU"`), как и остальная документация. Коммиты и заголовки PR остаются на английском по конвенции выше.
- **Контекст Jira.** CodeRabbit подключается к Jira (`knowledge_base.jira`, проект `OVE`) и сверяет PR с задачей — описанием и критериями приёмки. Но контекст подтягивается, только если **в теле PR стоит полная ссылка на задачу** — ключа `OVE-` в заголовке для этого мало (заголовок нужен Jira, тело — CodeRabbit). Добавляй в описание PR строку вида `Closes https://<ваш-домен>.atlassian.net/browse/OVE-42`.
