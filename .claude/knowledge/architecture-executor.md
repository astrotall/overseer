# Архитектура: `apps/executor` и COM-контроллеры

Общий контекст (раскладка `apps/` и `libs/`, `apps/api`, протокол инструмента `libs/tools/base.py`,
`ToolResult`) — в [architecture.md](architecture.md). Голосовой клиент — в
[architecture-voice.md](architecture-voice.md), браузер — в
[architecture-browser.md](architecture-browser.md).

## `apps/executor` — процесс на машине пользователя

**Отдельный процесс, работающий вне Docker, прямо в Windows-сессии пользователя** — «руки» агента
на конкретной машине. Отдельным процессом он нужен потому, что автоматизация десктопа принципиально
не запускается в контейнере:

- **COM / win32com** требует нативной Windows и интерактивной пользовательской сессии;
- **Playwright с реальным профилем браузера** — доступ к профилю, кукам, открытым сессиям;
- клавиатура, мышь, окна, скриншоты — доступ к рабочему столу.

В `docker-compose.yml` executor не входит и входить не должен.

**Транспорт до `api` спроектирован в OVE-29 и реализован в OVE-60** — Redis-список запросов,
персональный ключ ответа, heartbeat и ключ владения с TTL, доставка at-most-once, отдельный
ACL-пользователь Redis; см. «Транспорт `apps/api` ↔ `apps/executor`» и «Реализация (OVE-60)» ниже.
Контроллер о транспорте не знает: это класс с async-методами, и как запрос до него дошёл, решает
транспорт. Запуск: `uv run python -m apps.executor.main` (на Windows, после
`uv sync --group executor`).

## `ExcelController` (OVE-41) — первый COM-контроллер

Тонкая тестируемая обёртка над автоматизацией Excel через win32com. Стоит **под** слоем `Tool`:
инструментов Excel этот тикет не приносит, их будет звать следующий. Это первый COM-контроллер в
проекте, поэтому он же задаёт образец для контроллера Word (OVE-30/33): всё, что не зависит от
Excel, лежит в общих модулях и Word берёт его как есть.

Публичные методы — ровно три плюс жизненный цикл:

| Метод | Что делает |
|---|---|
| `open_or_create_workbook(path)` | `None` — новая книга без пути; путь к существующему файлу — открыть; путь к несуществующему — новая книга, привязанная к этому пути (запишется на `save()`) |
| `write_range(sheet, start_cell, data, *, formulas=False)` | записать прямоугольный блок значений, начиная с ячейки в нотации A1 |
| `save(path=None, *, overwrite=False)` | без пути — сохранить туда, к чему привязана книга; с путём — «сохранить как» |
| `release(conversation_id)` | закрыть книгу разговора, только если в ней нет несохранённых изменений (OVE-60) |
| `start()` / `aclose()` / `async with` | поднять и погасить STA-поток (и вместе с ним экземпляр Excel) |

С OVE-60 у трёх рабочих методов есть keyword-only `conversation_id`: книга держится **на
разговор** (см. «Книга на разговор» ниже). Без аргумента все вызовы идут в одну общую область —
прежнее поведение, на нём стоят тесты контроллера.

Операций чтения нет намеренно — это скоуп тикета, а не недосмотр.

├── lease.py            # владение очередью + heartbeat: SET NX, продление CAS-скриптом (OVE-60)
├── consumer.py         # цикл приёма, ответы, Dispatcher (порт), ExecutorService      (OVE-60)
├── dispatch.py         # закрытое отображение «тип запроса → обработчик»               (OVE-60)
├── paths.py            # PathPolicy: разрешённые папки поверх проверки контроллера    (OVE-60)
├── com.py              # Office-wide: платформенный гард, ленивый импорт pywin32, HRESULT → исключения
├── sta.py              # Office-wide: StaThread (выделенный поток + маршалинг) и ThreadAffinity
└── excel/

    ├── controller.py   # ExcelController: валидация → маршалинг на STA-поток → результат

`com.py` и `sta.py` про Excel не знают ничего — контроллер Word возьмёт их без правок. Фейковый
бэкенд живёт в тестах (`tests/executor_support.py`, общий для тестов контроллера, диспетчера и
разговоров), а не в пакете.

### Платформенный гард: импортируется везде, работает только на Windows

**Каждый модуль `apps/executor` импортируется на macOS, Linux и в CI.** `pythoncom`, `pywintypes`,
`win32com`, `win32api`, `win32event`, `win32process` импортируются лениво, внутри
`load_pywin32()` (`com.py`), а её зовёт только `Win32ExcelBackend.enter_thread()` — то есть первый
реальный запуск. Тот же приём, что у `OpenWakeWordDetector` и `PlaywrightBrowserBackend`.

Первое реальное использование вне Windows — `ConfigurationError` с понятным текстом
(`NOT_WINDOWS_TEXT`); на Windows без pywin32 — `ConfigurationError` с командой установки
(`PYWIN32_MISSING_TEXT`). Создать `Win32ExcelBackend` и `ExcelController` можно где угодно: отказ
случается на `start()`, а не на конструкторе и не на импорте.

Правило не на честном слове: `tests/unit/test_executor_ci_isolation.py` поднимает подпроцесс с
блокирующим `sys.meta_path`-финдером (как `test_voice_ci_isolation.py`) и импортирует каждый
модуль пакета, а заодно конструирует контроллер с настоящим бэкендом.

**Зависимость — группа `executor`** (`pywin32>=310; sys_platform == 'win32'`). Маркер платформы
нужен, потому что у pywin32 нет колёс под macOS и Linux: без него `uv sync --group executor`
упал бы на машине разработчика. `uv.lock` универсальный и содержит pywin32 с тем же маркером;
`uv sync --dev`, `uv sync --all-groups` и CI (`uv sync --dev --group browser`) на macOS/Linux его
не ставят — проверено на macOS. На Windows: `uv sync --group executor`.

### STA-поток: все COM-вызовы — на одном выделенном потоке

COM-объекты Office живут в однопоточной квартире (STA): объект, созданный в потоке, можно трогать
только из этого потока, а поток должен быть инициализирован `CoInitialize` до первого вызова и
закрыт `CoUninitialize` после последнего. Executor — asyncio-процесс, и event loop для этого не
годится: COM-вызов в Excel блокирует на секунды, а пул `asyncio.to_thread` выдаёт **разные**
потоки на разные вызовы — объект, созданный в одном, был бы потом тронут из другого.

Поэтому `StaThread` (`sta.py`) — **один** `threading.Thread` на контроллер:

- первым делом в потоке зовётся хук `initialize` (у реального бэкенда — `CoInitialize`), последним —
  `finalize` (закрыть книги, `Quit`, `CoUninitialize`, см. ниже). Если `initialize` упал, поток
  выходит, `finalize` не зовётся, а исключение (тот самый `ConfigurationError`) получает каждый
  ожидающий и каждый следующий вызов;
- `call(fn)` кладёт замыкание в очередь, поток исполняет его и резолвит future через
  `loop.call_soon_threadsafe`. Event loop ждёт результат и COM-объекта не касается никогда;
- в простое поток зовёт хук `idle` (у реального бэкенда — `pythoncom.PumpWaitingMessages()`):
  STA-поток, который не прокачивает сообщения, может подвесить чужие широковещательные рассылки
  оконных сообщений. Кадр опроса — `POLL_INTERVAL_S = 0.05`.

**COM-объекты не покидают STA-поток вовсе.** Порт возвращает контроллеру не объект книги, а
`WorkbookHandle` — целое число, по которому бэкенд держит объект у себя. Иначе ссылка на объект
доехала бы до event loop, и её `Release()` случился бы там, где её освободил сборщик мусора.
Вдобавок `Win32ExcelBackend` проверяет `ThreadAffinity` в каждом методе: вызов из чужого потока —
`RuntimeError`, а не тихий межквартирный вызов.

Уроки жизненного цикла `apps/voice` (OVE-45/47) перенесены целиком и закрыты тестами
(`tests/unit/test_executor_sta.py`):

- `start()` и `stop()` — под своим `threading.Lock`; `start()` на живом потоке — `RuntimeError`;
- `stop()`, не дождавшийся джойна, **оставляет ссылку на поток**, пишет
  `executor.sta_stop_timed_out` и возвращает `False`; следующий `start()` поэтому падает, а не
  заводит второй поток рядом с зависшим. Мёртвую ссылку `start()` подбирает сам;
- **каждый future резолвится всегда.** Ожидающие вызовы ведутся списком `_pending` от постановки в
  очередь до резолва; `stop()` резолвит их все `StaThreadUnavailableError` — и тот, что висит в
  COM-вызове, и те, что ждут в очереди. Поток на выходе делает то же самое. Новые вызовы после
  остановки не принимаются: проверка «принимаем ли» и постановка в список идут под одним локом с
  финальной разборкой, поэтому вызов не может проскочить в очередь, которую уже никто не читает;
- **двойной резолв — безопасный no-op**: `_settle` молча выходит на уже решённом future (тот же
  приём, что в `playback.py`). Так поздний ответ зависшего вызова после `stop()` не кидает
  `InvalidStateError` в обработчик исключений цикла;
- резолв после закрытого цикла (`RuntimeError` из `call_soon_threadsafe`) глотается с `debug`.

**Вызов, чей ожидающий сдался, не исполняется.** На future висит done-колбэк, который ставит флаг
`settled`; поток, достав такой вызов из очереди, его пропускает. Это и есть механика таймаута
(ниже) и отмены: запись, которую уже никто не ждёт, не должна случиться в мире позже.

### Таймаут вызова и остановка

`ExcelController` ограничивает каждый вызов `CALL_TIMEOUT_S = 60` через `asyncio.timeout()`.
Истёк — `OfficeTimeoutError` («выполнилась ли операция, неизвестно»). Различение с
`TimeoutError`, который бросил бы сам бэкенд, — по `scope.expired()`, а не по типу.
Это **не** `OfficeBusyError`, и смешивать их нельзя: `RPC_E_CALL_REJECTED` значит «вызов не
выполнен, повтори», а таймаут — «вызов, возможно, ещё выполняется». Повторять запись после
таймаута — значит, возможно, записать дважды.

Не начавшийся вызов после таймаута пропускается (флаг `settled`); начавшийся остаётся в COM, и
последующие вызовы встают за ним в очередь — и тоже истекают. `aclose()` поэтому **не берёт лок
операций**: иначе он ждал бы за зависшим вызовом. Он останавливает поток напрямую
(`STOP_TIMEOUT_S = 30` на джойн, через `asyncio.to_thread`, чтобы не блокировать цикл), и
зависший вызов получает `StaThreadUnavailableError` сразу. Финализация (закрытие книг, `Quit`) в
этом случае случится, только когда COM-вызов вернётся — поток daemon, принудительно его не убить.

Последовательность операций внутри контроллера держит `asyncio.Lock`: состояние «какая книга
открыта» меняется только в одном месте за раз.

### Свой экземпляр Excel, а не пользовательский: `DispatchEx`

Варианта два: подключиться к уже запущенному Excel пользователя (`GetActiveObject`) или запустить
собственный (`win32com.client.DispatchEx`). **Выбран собственный экземпляр.** Подключение к чужому
проигрывает по всем пунктам:

- всё, что автоматизации приходится выключать (`DisplayAlerts`, обработчики событий, макросы),
  выключилось бы в сессии пользователя — посреди его работы, и упавший процесс оставил бы это
  выключенным;
- человек, редактирующий ячейку, держит Excel в модальном состоянии: каждый вызов получал бы
  `RPC_E_CALL_REJECTED`, то есть автоматизация не работала бы ровно тогда, когда пользователь за
  компьютером;
- книги агента открывались бы в окне пользователя, а его книги были бы досягаемы для агента;
- `Quit()` из такого режима закрыл бы пользователю Excel.

`Dispatch` (без `Ex`) тоже не берётся: на практике pywin32 он известен тем, что может вернуть уже
запущенный Excel, тогда как `DispatchEx` явно создаёт новый экземпляр COM-сервера (на Windows это
не проверено — см. «Что проверено и что нет»). Цена собственного экземпляра — секунды
на старт процесса и сотни мегабайт памяти, поэтому он запускается лениво, на первом
`open_or_create_workbook`, а не на `start()`.

### Правило «не трогай Excel пользователя»

1. **`Quit()` зовётся только у экземпляра, который запустил контроллер.** Других у него нет: к
   чужим он не подключается вовсе.
2. **Закрываются только книги, которые контроллер открыл или создал** — бэкенд ведёт их таблицу
   (`WorkbookHandle → объект`). Закрытие — `Close(SaveChanges=False)`: несохранённое агентом не
   сохраняется молча.
3. **Модальные диалоги подавлены.** Сразу после запуска: `Visible = False`,
   `DisplayAlerts = False`, `AskToUpdateLinks = False`, `EnableEvents = False`,
   `AutomationSecurity = msoAutomationSecurityForceDisable` (3). Последние два — ещё и защита:
   путь к книге выбирает модель, и макросы `Workbook_Open` из такого файла не исполняются.
   Открытие — `UpdateLinks=0`, `Notify=False`, `IgnoreReadOnlyRecommended=True`,
   `AddToMru=False` (книги агента не попадают в список недавних файлов пользователя).
4. **Чужая книга в нашем экземпляре — экземпляр не гасится, а передаётся пользователю.**
   Невидимый экземпляр теоретически может получить книгу, открытую пользователем (оболочка Windows
   открывает файл в уже запущенном Excel). Поэтому перед `Quit()` бэкенд сверяет
   `Workbooks.Count` с числом своих книг: если чужие есть, он **восстанавливает все
   настройки, которые менял** (значения, прочитанные до изменения), делает экземпляр видимым
   (`Visible = True`, `UserControl = True`) и уходит, не вызывая `Quit()`. Это и есть ответ на
   «восстанови настройки, если работал в экземпляре пользователя»: в обычном режиме экземпляр
   свой и восстанавливать нечего, а в единственном случае, когда он стал наполовину чужим, —
   восстанавливается. `IgnoreRemoteRequests` для изоляции не используется: эта настройка
   сохраняется в профиле пользователя, и упавший executor оставил бы ему сломанное открытие
   файлов двойным кликом.
5. **Никакого осиротевшего `EXCEL.EXE`.** При старте бэкенд берёт PID процесса (`Hwnd` →
   `GetWindowThreadProcessId`) и держит его хэндл открытым (`OpenProcess(SYNCHRONIZE |
   PROCESS_TERMINATE)`): пока хэндл открыт, PID не переиспользуется другим процессом. На
   финализации — закрыть свои книги → `Quit()` → отпустить все ссылки → `gc.collect()` →
   `CoUninitialize()` → ждать выхода процесса до `REAP_TIMEOUT_MS = 5000`. Не вышел —
   `TerminateProcess` и `warning` `excel.orphan_terminated`. Терминация разрешена **только если
   `Quit()` был вызван**, то есть чужих книг в экземпляре не было; при передаче экземпляра
   пользователю (п. 4) процесс не трогается.
6. **Несохранённое не теряется и на остановке (OVE-60).** Финализация закрывает только чистые
   книги агента. Книга с несохранёнными изменениями (`Saved = False`) остаётся открытой, в лог
   уходит `excel.unsaved_workbooks_kept`, а экземпляр передаётся пользователю тем же путём, что в
   п. 4: видимым, с восстановленными настройками и без `Quit()`. Молча выбросить чужую работу
   нельзя, сохранить её поверх файла молча тоже нельзя, поэтому решает человек. На Windows не
   проверено.

### Безопасность данных от модели

Данные для записи приходят от модели, поэтому всё проверяется чистым кодом
(`validation.py`) **до** первого COM-вызова — невалидная запись до бэкенда не доходит вовсе
(пришпилено тестом):

| Проверка | Правило |
|---|---|
| форма | непустой список непустых строк одинаковой длины; строка вместо списка — ошибка |
| типы | только `str`, `int`, `float`, `bool`, `None`; `Decimal`, `bytes`, словари, вложенные списки — ошибка |
| размер | не больше `MAX_WRITE_CELLS = 10_000` ячеек за вызов; длина отсекается до обхода ячеек. С OVE-60 `MAX_WRITE_CELLS`, `MAX_CELL_TEXT_CHARS` и `MAX_SHEET_NAME_CHARS` не определяются в `validation.py`, а импортируются из `libs/schemas/executor.py` (`MAX_CELLS`, `MAX_CELL_TEXT_CHARS`, `MAX_SHEET_CHARS`): один источник для провода и контроллера, `libs` при этом `apps` не импортирует. Тест разбирает AST модуля и падает, если имя снова присвоят локально |
| числа | `NaN` и бесконечность запрещены; целые длиннее 15 знаков (`MAX_EXACT_INTEGER`) — ошибка: Excel хранит 15 значащих цифр и молча испортил бы номер карты или ИНН — такое число надо передать строкой |
| текст | не длиннее `MAX_CELL_TEXT_CHARS = 32_767` (предел ячейки Excel) |
| ячейка | одна ячейка A1, регистр не важен, `$` допускается: `A1`, `aa10`, `$C$7`; столбцы до `XFD`, строки до 1 048 576; диапазон, вылезающий за лист, — ошибка |
| лист | 1–31 символ, без `: \ / ? * [ ]`, без апострофа по краям, не `History` |
| путь | абсолютный путь Windows (`PureWindowsPath`, проверяется на любой ОС), расширение `.xlsx` / `.xlsm` / `.xlsb` / `.xls`, не длиннее 218 символов (предел Excel) |

Тексты ошибок — фиксированные фразы с позицией («Строка 2, столбец 3: …»), годные для модели.
Путь в текст ошибки не попадает вовсе; адрес ячейки и имя листа повторяются, но обрезаются до
`MAX_ECHOED_CHARS = 40`.

#### Формулы: по умолчанию любая строка — литеральный текст

Присвоение строки `Range.Value` через COM Excel разбирает так же, как ввод с клавиатуры:
`"=HYPERLINK(...)"` становится формулой, `"+1+1"`, `"-1"` и `"@SUM(A1)"` — тоже, а `"00123"` —
числом 123. Для данных от модели это прямой путь к formula injection: модель, начитавшаяся чужой
страницы, пишет в отчёт пользователя формулу, которая исполнится у него на открытии.

**Решение: при `formulas=False` (дефолт) каждая непустая строка пишется с префиксом-апострофом**
(`TEXT_PREFIX = "'"`) — Excel хранит её как текст, апостроф не входит в значение ячейки и виден
только в строке формул. Префикс ставится **любой** строке, а не только начинающейся с `= + - @`:
так закрыта и тихая порча данных (`"00123"`, `"1/2"` как дата), а правило читается одной фразой
«строка — значит текст». Числа, `bool` и `None` идут как есть; пустая строка — тоже, без префикса.

**Формулы — только явным `formulas=True`**, и даже тогда формулой считается лишь строка,
начинающаяся с `=`; `+`, `-` и `@` (унаследованные от Lotus формы ввода формул) остаются текстом.
Дефолт и опт-ин доказаны тестами на уровне payload, который получает бэкенд
(`test_formula_strings_are_written_as_literal_text_by_default`,
`test_formulas_are_written_only_on_explicit_opt_in`); живой тест на Windows проверяет то же самое
по `HasFormula` сохранённой книги.

### Листы и сохранение

- **Лист ищется без учёта регистра** (как это делает Excel), и в результат возвращается
  существующее написание: запрос `лист1` пишет в `Лист1`.
- **Отсутствующий лист создаётся** (в конец книги) — это не разрушительное действие, а
  `WriteResult.sheet_created` говорит вызывающему, что так случилось. Подводный камень, о котором
  должен знать будущий инструмент: имя листа новой книги зависит от языка Office (`Sheet1` /
  `Лист1`), и модель, написавшая в `Sheet1` на русском Excel, получит второй лист рядом с пустым
  `Лист1`. Решается чтением имён листов, а чтение — не скоуп OVE-41.
- **`save()` без пути** сохраняет туда, к чему книга привязана; у новой книги без пути — ошибка.
  **С путём**, совпадающим с текущим (без учёта регистра), — обычный `Save()`; с другим —
  `SaveAs` в формате по расширению (`.xlsx` 51, `.xlsm` 52, `.xlsb` 50, `.xls` 56), после чего
  книга привязана к новому пути.
- **Перезапись чужого файла — только по `overwrite=True`.** С `DisplayAlerts = False` Excel
  перезаписал бы файл молча, а перезапись — необратимое действие из [product.md](product.md).
  Без флага — `OfficeFileExistsError`; решать, спрашивать ли пользователя, будет слой `Tool`
  (`requires_confirmation`). Проверка существования и `SaveAs` — два шага, окно между ними не
  закрыто.
- **Переключение на другую книгу при несохранённых изменениях — `OfficeUnsavedChangesError`**,
  а не молчаливая потеря данных. Метода «закрыть книгу» в скоупе нет, поэтому правило такое:
  чистая текущая книга закрывается, но **после** того, как новая открылась (сбой открытия
  оставляет текущую на месте); повторное открытие той же книги — no-op.
- Открытая книга, оказавшаяся `ReadOnly` (файл держит другой процесс, и Excel без диалога открыл
  его только для чтения), сразу закрывается и даёт `OfficeFileLockedError`, а не ошибку на
  `save()` после всех записей.

### Типизированные исключения: здесь слой под `Tool` есть

Для браузерных инструментов типизированные исключения отклонены (см. «Ошибки браузерных
инструментов» в [architecture-browser.md](architecture-browser.md)): там место, где сбой
обнаружен, и место, где решают, что сказать модели, — один метод. Здесь — нет: контроллер
бросает, а инструмент над ним (и не один — Word, Excel) решает, как об этом сказать. Ровно тот
случай, ради которого исключения и существуют, — поэтому они в `libs/core/exceptions.py` и
**общие для Office**, а не Excel-специфичные:

| Исключение | Когда |
|---|---|
| `OfficeError` | база; несёт `hresult: int \| None` (без знака) |
| `OfficeInputError` | аргументы не прошли валидацию, нет открытой книги, некуда сохранять |
| `OfficeFileExistsError` | «сохранить как» на существующий файл без `overwrite=True` |
| `OfficeUnsavedChangesError` | переключение на другую книгу при несохранённых изменениях |
| `OfficeNotInstalledError` | `REGDB_E_CLASSNOTREG` (0x80040154), `CO_E_CLASSSTRING` (0x800401F3) |
| `OfficeBusyError` | `RPC_E_CALL_REJECTED` (0x80010001), `RPC_E_SERVERCALL_RETRYLATER` (0x8001010A), `VBA_E_IGNORE` (0x800AC472) |
| `OfficeFileLockedError` | `E_ACCESSDENIED`, `ERROR_SHARING_VIOLATION`, `ERROR_LOCK_VIOLATION` как HRESULT (0x80070005/20/21), `STG_E_ACCESSDENIED/SHAREVIOLATION/LOCKVIOLATION` (0x80030005/20/21), книга открылась только для чтения |
| `OfficeTimeoutError` | вызов не уложился в `CALL_TIMEOUT_S`; результат неизвестен |
| `OfficeComError` | любой другой COM-сбой |

`OfficeError` наследует `OverseerError`, а не `ConfigurationError`: Excel, которого нет, — сбой,
о котором модель сообщит пользователю, а не сломанная конфигурация процесса. `ConfigurationError`
остаётся ровно за платформенным гардом (не Windows, нет pywin32).

**Разбор HRESULT** (`map_com_error()` в `com.py`) идёт по `pywintypes.com_error` duck-typing'ом —
атрибуты `hresult`/`excepinfo` или `args` — поэтому он целиком тестируется без Windows. pywin32
отдаёт HRESULT знаковым, код нормализуется `& 0xFFFFFFFF`. Если верхний код —
`DISP_E_EXCEPTION` (0x80020009), решает `scode` из `excepinfo`: Office заворачивает в него
почти всё. Оговорка: собственная ошибка Excel 0x800A03EC — универсальная (ей Excel отвечает и на
«файл недоступен», и на неверный аргумент), поэтому она честно уходит в `OfficeComError`, а не
угадывается.

**Текст COM-ошибки в исключение не попадает.** `description` у Office регулярно содержит путь
(`'C:\Users\ivan\Документы\Зарплаты.xlsx' is read-only`), а сообщение исключения позже
окажется в `ToolResult`, то есть у стороннего LLM-провайдера, — тот же довод, что у редакции
ошибок инструментов в OVE-20. Поэтому сообщения — фиксированные фразы `ERROR_TEXTS` с одним
подставляемым именем приложения. **Полная деталь уходит в лог** (`office.com_error`: операция,
`hresult`, `scode`, `source`, `description`; `warning` для распознанных кодов, `error` с
трейсбеком для `OfficeComError`) и в `__cause__` исключения — для оператора, не для модели.
Обёртка — контекстный менеджер `translate_com_errors(com_error_type, application=, operation=)`:
Word возьмёт её тем же вызовом.

Повтора на `OfficeBusyError` нет: стандартное лечение — `IMessageFilter`, который сам повторяет
отклонённые вызовы, — в скоуп не вошло.

### Что проверено и что нет

**Проверено здесь (macOS, CI-эквивалент):** импорт всех модулей без pywin32 (блокирующий
финдер), отказ вне Windows и без pywin32, разбор A1 (включая `AA1`, `XFD1048576`), валидация
листов, данных, путей и лимита, формулы по умолчанию и по опт-ину, маршалинг (все вызовы бэкенда,
`enter_thread` и `exit_thread` — на одном потоке, и это не поток цикла), `start`/`stop` под
гонками, резолв каждого future, двойной резолв, таймаут и пропуск неначатого вызова, все пары
HRESULT → исключение на фейковых `com_error`, редакция текста ошибки. Ключевые тесты проверены
мутациями: снятие префикса формул, обнуление ссылки на поток при таймауте `stop()`, снятие защиты
от двойного резолва, `stop()` без резолва ожидающих, исполнение вызова на потоке цикла,
исполнение вызова, чей ожидающий уже сдался, игнорирование `scode` и снятие лимита ячеек — каждая
мутация роняет тесты.

**Не проверено — на Windows не запускалось ни разу.** Тесты с живым Excel написаны
(`tests/integration/test_excel_com_windows.py`, `@pytest.mark.windows`), но всё ниже — ожидания
по документации, а не наблюдения:

- что `DispatchEx` действительно не подключается к запущенному Excel пользователя;
- что присвоение `Range.Value` строки с апострофом даёт текстовую ячейку без формулы, а
  `pythoncom.Empty` в массиве — пустую ячейку;
- что именованные аргументы `Workbooks.Open(...)` / `SaveAs(...)` / `Worksheets.Add(After=...)`
  проходят через динамический dispatch pywin32;
- что Excel с `DisplayAlerts = False` открывает занятый файл только для чтения, а не падает —
  отсюда ветка `ReadOnly` → `OfficeFileLockedError`;
- что `Hwnd` невидимого экземпляра даёт PID, а `Quit()` + `CoUninitialize()` гасит процесс за
  `REAP_TIMEOUT_MS` и терминация в норме не нужна;
- что HRESULT-коды выше — те, которые Excel реально отдаёт в соответствующих ситуациях;
- что целые вне int32 нужно приводить к `float` (`VT_I8` старые версии Excel не принимают) —
  перестраховка, а не замер;
- что `PumpWaitingMessages()` раз в 50 мс достаточно и не мешает.

Первый прогон на Windows (`uv sync --group executor`, затем `uv run pytest -m windows`)
подтвердит это или покажет, где ожидание неверно.

## Транспорт `apps/api` ↔ `apps/executor` (OVE-29)

Как вызов инструмента, решённый внутри `apps/api` (Docker), доходит до `apps/executor` (отдельный
Windows-процесс на рабочем столе пользователя, вне Docker) и как возвращается результат. OVE-29 —
дизайн-тикет: решение записано здесь, а исполняемый артефакт у него один — **контракт сообщений**
(`libs/schemas/executor.py`) плюс **порт** `ExecutorClient` с фейком (`libs/executor/`).
Реализацию обеих сторон, ACL-изоляцию, разрешённые папки и книгу на разговор принёс OVE-60 — что из
дизайна изменилось по ходу и замеры вместо оценок, см. «Реализация (OVE-60)» ниже.

### Что проверено перед решением

| Что | Как проверено | Результат |
|---|---|---|
| адрес, на котором опубликован Redis | `docker/docker-compose.yml` (`"${REDIS_PORT:-56379}:6379"`, без IP), затем `docker port overseer-redis` и `lsof` на поднятом контейнере | **`0.0.0.0:56379` и `[::]:56379`** — все интерфейсы хоста, не `127.0.0.1` |
| пароль и защищённый режим Redis | `redis-cli CONFIG GET requirepass / protected-mode / bind`, `ACL LIST` внутри контейнера | `requirepass` пуст, `protected-mode no`, `bind * -::*`, `user default on nopass … +@all` |
| доступен ли Redis из сети | `PING` через `nc` на LAN-адрес машины разработчика, порт 56379 | **`+PONG` без аутентификации** |
| почему так | документация Docker (port publishing): «By default, when a container's ports are mapped without any specific host address, the Docker daemon publishes ports to all host addresses (`0.0.0.0` and `[::]`)» и «Publishing container ports is insecure by default»; Docker Hub, образ `redis`, раздел Security: «the "Protected mode" is turned off by default … it will be open without a password to anyone» | поведение — дефолт Docker плюс дефолт образа, а не ошибка в нашем compose-файле, но compose его не исправляет |
| как `apps/api` и процесс на хосте видят Redis | compose: `api` получает `REDIS_URL: redis://redis:6379/0` (имя сервиса во внутренней сети); `.env.example`: `REDIS_URL=redis://localhost:56379/0` (опубликованный порт хоста) | у executor — **свой** адрес через опубликованный порт, см. «Настройки executor» |
| доставка pub/sub | redis.io, Pub/Sub, Delivery semantics: «Redis' Pub/Sub exhibits at-most-once message delivery semantics … If the subscriber is unable to handle the message … the message is forever lost» | подписчик, которого нет, сообщение теряет молча, а отправитель об этом не узнаёт |
| списки | redis.io, `BLMOVE`/`LMOVE` (с 6.2.0), раздел «Pattern: Reliable queue» | блокирующее чтение списка и паттерн «processing list» для at-least-once существуют; нам нужен обратный, at-most-once, вариант — см. ниже |
| Arq | PyPI `arq` (0.28.0 от 16.04.2026), README, `arq/worker.py` на `main`, документация «Jobs may be called more than once!» | классификаторы ОС — только `POSIX :: Linux` и `Unix`, Windows не заявлен; README: «In maintenance only mode»; `add_signal_handler` обёрнут в `except NotImplementedError` (то есть на Windows воркер стартует, но без обработки SIGINT/SIGTERM); исполнение «пессимистичное» — задача, прерванная остановкой воркера, запускается снова; повторы отключаются `max_tries=1` или `retry_jobs=False` |
| сторона executor | `apps/executor/excel/controller.py`, `sta.py`, `libs/core/exceptions.py` | `CALL_TIMEOUT_S = 60`, `OfficeTimeoutError` значит «результат неизвестен», один STA-поток — вызовы строго последовательны |
| сторона api | `apps/api/services/chat.py` | `_execute()` зовёт `tool.execute()` внутри открытой транзакции хода: всё время ожидания executor ход держит соединение с PostgreSQL |

Первые пять строк таблицы — снимок на момент OVE-29. Находку закрыл OVE-59: порт Redis опубликован
только на `127.0.0.1`, Redis требует пароль, а с LAN-адреса подключение к портам Redis и PostgreSQL
отклоняется. Перепроверено на пересозданных контейнерах, подробности — «Доступ к PostgreSQL и
Redis» в [architecture.md](architecture.md).

Чего проверить не удалось (Windows в окружении разработки нет): что Windows-процесс достучится до
порта, опубликованного Docker Desktop, по `127.0.0.1`; поведение `redis-py` на Windows-цикле событий
(`ProactorEventLoop`); точный синтаксис ACL-селекторов Redis 7 из раздела «Безопасность» — его
сверяет тикет реализации на живом Redis 7.4 (сверено в OVE-60, см. «ACL-пользователь Redis»).

### Варианты

| Критерий | (a) pub/sub + канал ответа | **(b) список-очередь + ключ ответа + heartbeat** | (c) отдельная очередь Arq | (d) HTTP-сервер в executor |
|---|---|---|---|---|
| executor не запущен | не видно: `PUBLISH` вернёт 0 подписчиков, но 0 бывает и на гонке переподписки — нужен отдельный механизм живости | ключ heartbeat с TTL: нет ключа — нет executor, ответ за одно `GET` | живость воркера отдельно не выражена: задача просто ляжет в очередь и будет ждать | отказ в соединении — мгновенно |
| потеря при перезапуске стороны | сообщение без подписчика теряется молча | запрос лежит в списке; executor на старте видит истёкший `deadline` и отказывает | задача переживёт перезапуск и **исполнится позже** — против нашей семантики | запрос в полёте теряется, исход неизвестен |
| подтверждение и результат | нет ack; ответ теряется, если api переподписался | `accepted` и результат в персональном списке `reply:<id>`, `BLPOP` с таймаутом; «не взят» доказуемо через `LREM` | `job.result(timeout)` | синхронный ответ |
| порядок | порядок публикации | FIFO одного списка, один потребитель | очередь Arq | на усмотрение сервера |
| Windows | `redis-py` — чистый Python | то же | официально не заявлен, обработка сигналов отключена | нужен HTTP-сервер и правило брандмауэра Windows |
| новых движущихся частей | канал + отдельный heartbeat | четыре ключа, без новых зависимостей | вторая очередь и второй воркер Arq, библиотека в режиме «только поддержка» | HTTP-сервер, его аутентификация, адрес executor в конфиге api |
| безопасность | всё держится на доступе к Redis | всё держится на доступе к Redis — закрывается ACL и привязкой к loopback | то же, плюс произвольные имена функций в задачах | **входящий порт на машине пользователя** — новая поверхность атаки, нужен свой токен и TLS |

**Выбран (b).** Pub/sub проигрывает ровно там, где ожидалось: без хранения, без ack, и отличить
«executor лежит» от «executor медлит» нельзя, не изобретая рядом живость, — то есть (b) всё равно
пришлось бы строить, только поверх менее надёжного канала. Arq отпадает по двум независимым причинам:
Windows официально не поддерживается, а модель «лучше дважды, чем ни разу» прямо противоречит
необходимой нам at-most-once (её можно выключить, но тогда от Arq остаётся сериализация задачи —
то, что контракт ниже делает и так). HTTP даёт лучшую живость, но платит за неё входящим портом на
рабочем столе пользователя — ровно тем, чего «executor сам инициирует соединение» и позволял
избежать; Redis уже есть у обеих сторон. Redis Streams рассмотрены как вариант (b): группы
потребителей дают at-least-once и PEL, а at-most-once на них — это `XREADGROUP` с `NOACK` и
обрезка потока, то есть больше состояния без выигрыша против списка.

### Ключи и поток вызова

| Ключ | Тип | Пишет | Читает | Жизнь |
|---|---|---|---|---|
| `overseer:executor:requests` | список | api, `RPUSH` | executor, `BLPOP` | до прочтения; сам элемент несёт `deadline` |
| `overseer:executor:reply:<id>` | список | executor, `RPUSH` + `EXPIRE` | api, `BLPOP` | `reply_ttl_s` (60 с) |
| `overseer:executor:heartbeat` | строка, `ExecutorHeartbeat` в JSON | executor, `SET … EX` | api, `GET` | `heartbeat_ttl_s` (15 с), обновляется каждые 5 с |
| `overseer:executor:seen:<id>` | строка | executor, `SET NX EX` | executor | `dedup_ttl_s` (600 с) |
| `overseer:executor:owner` | строка, `instance_id` | executor, Lua-скрипт | executor | как heartbeat; добавлен в OVE-60, см. «Владение очередью» |

Сторона **api** (реализация `ExecutorClient.call()`):

1. `GET heartbeat`. Нет ключа — `executor_unavailable`; версия не та — `unsupported_version`;
   операции нет в `heartbeat.operations` — `unknown_operation`; Redis не отвечает —
   `transport_unavailable`. Всё это **до отправки**: исход «не выполнено» достоверен.
   `instance_id` из heartbeat запоминается.
2. `encode_request()` (потолок `MAX_REQUEST_BYTES`), `RPUSH requests <payload>`. Строка `payload`
   сохраняется — она нужна для `LREM`.
3. `BLPOP reply:<id>` с таймаутом `DEFAULT_PICKUP_TIMEOUT_S` (5 с). Ничего — `LREM requests 1
   <payload>`: удалил `1` — запрос не взят, и взять его теперь некому (`LREM` и `BLPOP` атомарны
   относительно друг друга) → `not_picked_up`, «не выполнено» достоверно. Удалил `0` — executor
   его уже забрал, ждём дальше.
4. Ожидание результата идёт **срезами** не длиннее пяти секунд до `deadline`. После каждого пустого
   среза — повторный `GET heartbeat`: ключ пропал или `instance_id` сменился (executor упал или
   перезапустился) — ждать нечего → `reply_timeout`, исход неизвестен.
5. Пришёл `result` → `parse_reply()` → ответ. Не разобрался — `malformed_reply`.
6. `deadline` наступил — `reply_timeout`. После `accepted` запрос **не** снимается: он уже исполняется.
7. Ход отменили (`CancelledError`) после `RPUSH` — экранированный `LREM` как в шаге 3, исход в лог,
   `CancelledError` пробрасывается.

Сторона **executor** (цикл приёма):

1. На старте `SET heartbeat <своё> NX EX`. Ключ уже есть с чужим `instance_id` — второй executor на
   том же Redis: процесс **отказывается стартовать** (`ConfigurationError`). Дальше обновление
   heartbeat только при совпадении `instance_id` (сравнение и запись — одним Lua-скриптом, тем же
   приёмом, что `_CLAIM_SCRIPT` в `libs/confirmations/store.py`).
2. `BLPOP requests` → `parse_request()`. Ошибка контракта с разобранным `id` — ответ с кодом в
   `reply:<id>`; без `id` — только лог, отвечать некуда.
3. `SET seen:<id> NX EX` не прошёл — дубликат: **без исполнения и без ответа**, `warning`.
4. Своё «сейчас» ≥ `deadline` — ответ `deadline_exceeded`, без исполнения.
5. `RPUSH reply:<id> accepted`.
6. Проверка путей по политике executor (ниже) — `path_not_allowed`.
7. Вызов контроллера. `OfficeError` → `error_code_for()`; любое другое исключение →
   `internal_error`, полный трейсбек — в локальный лог executor.
8. `encode_reply()` (потолок `MAX_REPLY_BYTES`; не влезло — `internal_error`), `RPUSH` + `EXPIRE`.

**Порядок** — FIFO одного списка и одного потребителя, исполнение строго последовательное (STA-поток
один). Вызовы одного хода `ChatService` и так идут друг за другом; конкурируют только разные
разговоры, и для них очередь — честный порядок поступления.

**`conversation_id` на проводе не для красоты.** У `ExcelController` есть состояние — «какая книга
открыта», — и два разговора, делящие один контроллер, писали бы в книги друг друга. Executor поэтому
выбирает контроллер по `conversation_id` (контроллер на разговор, с закрытием по простою и потолком —
тем же приёмом, что `BrowserSessionManager`). Детали жизненного цикла — тикет реализации.

### Живость: отказ за миллисекунды, а не за таймаут

Запуск `apps/api` от executor **не зависит**: клиент не ходит в Redis на старте, отказ случается на
вызове и приходит модели обычным `ToolResult` — то же решение, что у необязательного Playwright.
Сколько ход держит соединение с PostgreSQL в каждом случае:

| Ситуация | Сколько ждёт api | Исход |
|---|---|---|
| executor не запущен (heartbeat истёк) | одно `GET`, миллисекунды | `executor_unavailable`, не выполнено |
| executor упал меньше 15 с назад (heartbeat ещё жив) | пикап 5 с, затем `LREM` | `not_picked_up`, не выполнено |
| executor занят другим вызовом | пикап 5 с, затем `LREM` | `not_picked_up`, не выполнено |
| executor упал посреди вызова | до среза (5 с) + TTL heartbeat (15 с) ≈ 20 с | `reply_timeout`, неизвестно |
| executor жив, COM завис | до `deadline` (70 с); обычно раньше приходит `timeout` контроллера на 60 с | `timeout` / `reply_timeout`, неизвестно |

`DEFAULT_CALL_BUDGET_S = 70` выбран больше `CALL_TIMEOUT_S = 60` контроллера, чтобы типизированный
`timeout` от executor приходил раньше, чем api сдастся сам, а пикап в 5 с гарантирует, что
взятому запросу остаётся не меньше 65 с. Последний ряд — единственный случай, когда соединение
держится долго, и это тот же принятый риск, что у LLM-вызова (см. «Удержание DB-соединения» в
[architecture.md](architecture.md)): executor жив, просто Excel медленный.

**Часы.** `deadline` абсолютный, и executor сверяет его со своими часами. В v1 обе стороны на одной
машине (Docker Desktop и рабочий стол), поэтому расхождение мало. Если часы executor убегут вперёд
больше бюджета, все вызовы будут честно отклоняться как `deadline_exceeded` — громко, а не молча.
`heartbeat.sent_at` позволяет api писать `warning` при расхождении больше интервала heartbeat.

### Семантика доставки: at-most-once

Вызов COM, истёкший по таймауту, мог выполниться (см. «Таймаут вызова и остановка»), а значит
автоматический повтор — это возможная двойная запись или двойное сохранение. Поэтому:

- **api не повторяет никогда.** Ни клиент, ни инструмент над ним. Решение о повторе принимает модель,
  прочитав, что исход неизвестен, — и если инструмент помечен `requires_confirmation`, повтор снова
  пройдёт через подтверждение пользователя.
- **executor не перечитывает взятое.** `BLPOP`, а не `BLMOVE` в processing-список: паттерн «Reliable
  queue» из документации Redis — это at-least-once, ровно то, от чего мы уходим. Executor, упавший
  посреди вызова, запрос теряет, и api сообщит «исход неизвестен».
- **дедупликация по `id`** — `SET seen:<id> NX EX dedup_ttl_s`. Дубликат не исполняется и не получает
  ответа (ответ ушёл бы в `reply:<id>` оригинала). `dedup_ttl_s` (600 с) больше
  `MAX_CALL_WINDOW_S` (120 с): запрос, повторённый после истечения дедупликации, к тому моменту уже
  просрочен и будет отклонён по `deadline`. Повтор отклоняется либо как дубликат, либо как
  просроченный — третьего не дано.

Что видит модель, когда исход неизвестен: одну фиксированную фразу `UNKNOWN_OUTCOME_TEXT`
(«выполнилось ли, неизвестно; не повторяй автоматически; скажи пользователю проверить») и
`summary` «Результат действия на компьютере пользователя неизвестен». Ни текста COM, ни HRESULT, ни
пути — тем же правилом, что у OVE-20 и OVE-41: подробности остаются в логе executor на машине
пользователя.

### Безопасность: канал запросов — граница доверия

Кто может записать в `overseer:executor:requests`, тот заставляет процесс на рабочем столе
пользователя открывать, писать и сохранять файлы. На момент OVE-29 это был **любой в локальной
сети**: Redis был опубликован на всех интерфейсах без пароля (см. проверку выше). OVE-29 compose не
менял, и находка блокировала реализацию транспорта. Её закрыл OVE-59 — пункты 1 и минимум пункта 2
ниже уже стоят в compose.

Требования, которые тикет реализации обязан выполнить:

1. **Привязка — сделано в OVE-59.** Порт Redis публикуется только на loopback:
   `127.0.0.1:${REDIS_PORT:-56379}:6379` (по документации Docker это ограничивает доступ самим
   хостом). v1 поддерживает ровно один сценарий — Docker и executor на одной машине. Executor на
   другой машине требует TLS Redis и отдельного решения; молча открывать порт наружу нельзя.
2. **Аутентификация.** Отдельные ACL-пользователи Redis (Redis 6+): `overseer-api` и
   `overseer-executor`. Пользователь executor ограничен ключами `overseer:executor:*` и только теми
   командами, что нужны циклу приёма; писать в `requests` он не должен (это делается ACL-селекторами
   Redis 7 — синтаксис сверяется на живом Redis в тикете реализации). Минимум — `requirepass` —
   стоит с OVE-59: пароль `REDIS_PASSWORD`, URL вида `redis://default:<пароль>@…`, где ACL заменит
   только имя пользователя и пароль. Секреты — в `.env`, не в репозитории. **OVE-60:** пользователь
   `overseer-executor` заведён и проверен на живом Redis (см. «ACL-пользователь Redis
   `overseer-executor`»); api и worker остаются на `default` — отдельного `overseer-api` нет.
3. **Allowlist операций.** Операция — это литерал дискриминированного объединения
   (`excel.open_or_create_workbook`, `excel.write_range`, `excel.save`), а не имя метода: executor
   разбирает запрос `parse_request()` и диспетчеризует по **типу модели** (`match`), а не через
   `getattr` по строке. Неизвестное имя — `unknown_operation`, лишнее поле на любом уровне —
   `malformed_request`. Произвольных callables, модулей, команд шелла на проводе нет и быть не может.
4. **Двойная валидация аргументов.** Контракт ограничивает только размер и типы (длины строк, число
   ячеек, `NaN`, строгие типы без приведения `"1"` → `1`). Содержательная проверка — та же
   `validation.py` контроллера (A1, имя листа, форма данных, формат пути); провод её не заменяет.
5. **Политика путей на стороне executor** — после `validate_workbook_path()` и до первого
   COM-вызова: путь приводится к абсолютному (`realpath`, то есть с раскрытием ссылок и junction'ов) и
   обязан лежать внутри одного из `EXECUTOR_ALLOWED_ROOTS`; отклоняются UNC (`\\server\share` — это
   ещё и утечка NTLM-хэша по SMB), device-пути (`\\?\`, `\\.\`), пути относительно диска и компоненты
   `..`. Отказ — `path_not_allowed`. **OVE-60:** сделано и расширено (альтернативные потоки, имена
   устройств, точки и пробелы в конце компонентов), а сверка идёт и до, и после `realpath` — см.
   «Разрешённые папки».
6. **Что executor отклоняет, даже если просят:** операции вне allowlist; неизвестную версию схемы;
   запрос больше `MAX_REQUEST_BYTES`; истёкший `deadline`; повторный `id`; путь вне разрешённых
   корней; работу при втором экземпляре executor на том же Redis.
7. **В ответе только коды.** `ExecutorError` — одно поле `code`; ответ с добавленным `message`
   отклоняется на разборе (`extra="forbid"`), так что сырой текст COM не просочится и случайно.

Подтверждение необратимых действий (`requires_confirmation`) остаётся на стороне api: executor не
может проверить, что пользователь сказал «да», и доверяет тому, кто имеет право писать в очередь.
Ровно поэтому пункты 1–2 — обязательные, а не «гигиена».

Подпись запросов HMAC общим секретом рассмотрена и в v1 отклонена: в нашем деплое право записи в
очередь и знание секрета совпали бы у одних и тех же процессов, а реальная дыра — неаутентифицированный
Redis — закрывается пунктами 1–2. Пересмотреть, если Redis станет общим за пределами одной машины.

### Контракт сообщений `libs/schemas/executor.py`

Pydantic v2, `extra="forbid"` везде, типизированные дискриминаторы — в духе `libs/schemas/ws.py`.
Версия схемы — `SCHEMA_VERSION = 1`, на проводе обязательное поле `schema_version`.

**Запрос** — объединение по `operation`, общая часть у всех вариантов:

```json
{
  "schema_version": 1,
  "id": "6f1c…",
  "conversation_id": "a2e9…",
  "issued_at": "2026-11-22T12:00:00Z",
  "deadline": "2026-11-22T12:01:10Z",
  "operation": "excel.write_range",
  "arguments": {"sheet": "Лист1", "start_cell": "A1", "data": [["Итого", 42]], "formulas": false}
}
```

| Модель | `arguments` |
|---|---|
| `OpenOrCreateWorkbookRequest` | `path: str \| None` |
| `WriteRangeRequest` | `sheet`, `start_cell`, `data: list[list[bool \| int \| float \| str \| None]]`, `formulas: bool = false` |
| `SaveWorkbookRequest` | `path: str \| None`, `overwrite: bool = false` |

Время — только с часовым поясом (`AwareDatetime`); `deadline` позже `issued_at` и не дальше
`MAX_CALL_WINDOW_S` (120 с) от него.

**Ответы** — объединение по `type`, оба в `reply:<id>`:

```json
{"type": "accepted", "schema_version": 1, "id": "6f1c…"}
{"type": "result", "schema_version": 1, "id": "6f1c…", "status": "ok",
 "data": {"sheet": "Лист1", "address": "A1:B1", "rows": 1, "columns": 2, "sheet_created": false}}
{"type": "result", "schema_version": 1, "id": "6f1c…", "status": "error", "data": {},
 "error": {"code": "file_locked"}}
```

`data` успешного ответа описан моделями `WorkbookOpened`, `RangeWritten`, `WorkbookSaved` — поля
совпадают с `WorkbookInfo` / `WriteResult` / `SaveResult` контроллера (пришпилено тестом).

**Heartbeat** — `ExecutorHeartbeat`: `schema_version`, `instance_id`, `started_at`, `sent_at`,
`operations` (что этот executor умеет; api отказывает `unknown_operation` до отправки).

**Потолки** (байты считаются в UTF-8, проверяются **до** разбора JSON): запрос — `MAX_REQUEST_BYTES`
(1 МиБ), ответ — `MAX_REPLY_BYTES` (64 КиБ), heartbeat — 4 КиБ. На отправке те же потолки
проверяют `encode_request()` / `encode_reply()`: api не может отправить, а executor — ответить
сообщением сверх лимита. Ячеек — не больше `MAX_CELLS` (10 000, равно `MAX_WRITE_CELLS`
контроллера), текст ячейки — не длиннее 32 767 символов, имя листа — 31, путь — 260 (Windows
`MAX_PATH`; контроллер строже, 218).

**Версия проверяется первой, до формы.** `parse_request()` читает сырой `schema_version` раньше
валидации: целое, но не `1` — `unsupported_version` (а не «лишнее поле», которое выдала бы модель на
запросе новой версии); не целое (в том числе `true`, `1.0`, `"1"`) — `malformed_request`. Модели и
сами не принимают `true` за `1` — pydantic по умолчанию принял бы. Для heartbeat то же правило: новая
версия executor с новыми полями опознаётся как несовпадение версий, а не как мусор.

**Ошибки разбора** — `ExecutorContractError(code, request_id, errors)`: код из того же
`ExecutorErrorCode`, `id`, если его удалось извлечь, и **типы** ошибок pydantic (`extra_forbidden`,
`missing`) для лога — без значений, тем же правилом, что `tool.invalid_arguments`. Исключение
наследует `ValueError`, а не `OverseerError`: это результат разбора, как `ValidationError`, и ловят
его ровно две точки — цикл приёма executor и клиент api.

**Коды ошибок и исходы** — `ExecutorErrorCode` и `ERROR_OUTCOMES`: у каждого кода один из двух
исходов, `not_executed` (достоверно не выполнено, можно чинить и повторять) или `unknown`.
Исключения `Office*` переводит `error_code_for()` (по MRO, так что подкласс наследует код родителя):

| Исключение | Код | Исход |
|---|---|---|
| `OfficeInputError` | `invalid_input` | не выполнено |
| `OfficeFileExistsError` | `file_exists` | не выполнено |
| `OfficeUnsavedChangesError` | `unsaved_changes` | не выполнено |
| `OfficeNotInstalledError` | `not_installed` | не выполнено |
| `OfficeBusyError` | `busy` | не выполнено |
| `OfficeFileLockedError` | `file_locked` | не выполнено |
| `OfficeTimeoutError` | `timeout` | **неизвестно** |
| `OfficeComError`, `OfficeError` | `com_error` | **неизвестно** — 0x800A03EC универсален, и сбой посреди записи не доказывает, что записи не было |

### Порт `ExecutorClient` (`libs/executor/`)

```python
class ExecutorClient(Protocol):
    async def call(self, request: ExecutorRequest) -> ExecutorResponse: ...
```

Контракт порта: **тотальный**, как `Tool.execute()`. Сбои транспорта не бросаются, а возвращаются
`ExecutorResponse.failed(request.id, <код>)` с кодами стороны api (`executor_unavailable`,
`transport_unavailable`, `not_picked_up`, `reply_timeout`, `malformed_reply`, `transport_error`,
`payload_too_large`, `unsupported_version`, `unknown_operation`); насквозь проходит только
`CancelledError`. Так у инструмента одна ветка разбора на любой исход.

Удалённый инструмент (OVE-31/32/42) — обычный наследник `Tool`, который в `_execute` собирает
запрос, зовёт порт и переводит ответ:

```python
response = await self._client.call(request)
if response.error is not None:
    return failure_result(response.error)
written = RangeWritten.model_validate(response.data)
return ToolResult.ok(...)
```

`failure_result()` берёт фиксированный текст из `FAILURE_TEXTS` (по одному на код, ни одной
подстановки) и короткий `summary` по исходу — «не выполнено» или «результат неизвестен». Тексты
общие, чтобы три инструмента не формулировали одно и то же трижды по-разному.

`FakeExecutorClient` (`libs/executor/fake.py`) — фейк для тестов инструментов. Он не подменяет
контракт, а **проходит его**: запрос кодируется и разбирается заново (потолки и `extra="forbid"`
работают как на настоящем проводе), ответ — тоже. Поведение повторяет описанное выше:
`running=False` → `executor_unavailable` без вызова обработчика; `failure="<код>"` — сценарий сбоя
транспорта; повторный `id` → обработчик не зовётся, исход `reply_timeout`; часы (`clock`) позже
`deadline` → `deadline_exceeded`; `OfficeError` из обработчика → его код; другое исключение →
`internal_error` без текста; ответ с чужим `id` не доставляется (`reply_timeout`); слишком большой
ответ → `malformed_reply`. Записанные запросы — в `requests`.

### Матрица отказов

| Ситуация | Что делает api | Код | Что говорят модели | Что в логах |
|---|---|---|---|---|
| executor не запущен | `GET heartbeat` → нет ключа, в очередь ничего не кладётся | `executor_unavailable` | executor не запущен, действие не выполнено, попроси пользователя его запустить | api: `executor.unavailable` |
| Redis недоступен из api | исключение `redis-py` до `RPUSH` | `transport_unavailable` | канал недоступен, не выполнено | api: `executor.transport_unavailable` с типом исключения |
| Redis оборвался после `RPUSH` | ждать нечего | `transport_error` | исход неизвестен, не повторяй | api: `executor.transport_error` |
| executor занят или только что упал | 5 с пикапа, `LREM` снял запрос | `not_picked_up` | занят, не выполнено, можно позже | api: `executor.not_picked_up` |
| executor упал или перезапустился посреди вызова | heartbeat пропал или сменил `instance_id` | `reply_timeout` | исход неизвестен | api: `executor.reply_timeout`, `reason=executor_lost` |
| `deadline` истёк на стороне api | перестаёт ждать | `reply_timeout` | исход неизвестен | api: `executor.reply_timeout`, `reason=deadline` |
| запрос пролежал в очереди дольше `deadline` | — (api уже ушёл) | `deadline_exceeded` | — (некому) | executor: `executor.deadline_exceeded` |
| executor не разобрал запрос | получает ответ-ошибку | `malformed_request` / `payload_too_large` | запрос некорректной формы, не выполнено — это ошибка сервера, а не модели | executor: `executor.request_rejected` с типами ошибок; api: `executor.call_finished` |
| ответ executor не разобрался | — | `malformed_reply` | исход неизвестен | api: `executor.malformed_reply` с типами ошибок |
| версии схемы не совпали | по heartbeat — до отправки; по запросу — ответ executor | `unsupported_version` | executor нужно обновить, не выполнено | api: `executor.version_mismatch` с обеими версиями |
| операция неизвестна executor | по `heartbeat.operations` — до отправки | `unknown_operation` | executor нужно обновить, не выполнено | api: `executor.unknown_operation` |
| путь вне разрешённых корней | получает ответ-ошибку | `path_not_allowed` | путь вне разрешённых папок, не выполнено | executor: `executor.path_not_allowed` (без пути) |
| типизированная ошибка Office | получает ответ-ошибку | `invalid_input`, `file_exists`, `unsaved_changes`, `not_installed`, `busy`, `file_locked` | фиксированная фраза на код, не выполнено | executor: `office.com_error` (OVE-41, с HRESULT и описанием — локально) |
| Excel не ответил за 60 с | получает ответ-ошибку | `timeout` | исход неизвестен | executor: `office.com_error` / таймаут контроллера |
| непредвиденный COM-сбой | получает ответ-ошибку | `com_error` | исход неизвестен | executor: `office.com_error` с трейсбеком |
| непредвиденное исключение в executor | получает ответ-ошибку | `internal_error` | исход неизвестен | executor: `executor.call_failed` с трейсбеком |
| повторный `id` | — (ответа нет, api получит `reply_timeout`) | — | — | executor: `executor.duplicate_request` |

Во всех строках в логи уходят `request_id`, `conversation_id`, операция, код, исход и длительность —
**никогда** аргументы, пути и данные ячеек: это данные пользователя, их место — аудит вызовов.
Итоговое событие каждого вызова на api — `executor.call_finished`.

### Настройки executor (OVE-60)

Свой класс, как `VoiceSettings`: `ExecutorSettings` в `apps/executor/config.py`, `env_prefix="EXECUTOR_"`,
тот же `.env`, `hide_input_in_errors=True`. Общий `Settings` не переиспользуется: executor едет на
машину пользователя, а поля БД и LLM ему не нужны. Юнит-тесты изолированы от окружения машины
фикстурой `hermetic_settings`: она снимает переменные `EXECUTOR_*` (и алиас `ENV`) и выключает чтение
`.env` у всех трёх классов настроек.

| Поле | Тип | Дефолт | Назначение |
|---|---|---|---|
| `redis_url` | `SecretStr \| None` | **нет** | `redis://overseer-executor:<REDIS_EXECUTOR_PASSWORD>@127.0.0.1:56379/0` — опубликованный порт хоста (имя `redis` есть только в сети Docker), литерал `127.0.0.1`, не `localhost`. Пусто — executor не стартует. Пароль — только URL-безопасные символы |
| `env` | `local \| dev \| prod` | `local` | читается из `EXECUTOR_ENV`, иначе из общего `ENV` |
| `heartbeat_interval_s` | `float` | `5.0` | как часто продлевать владение и heartbeat |
| `heartbeat_ttl_s` | `float` | `15.0` | TTL владения и heartbeat; валидатор: не меньше двух интервалов |
| `reply_ttl_s` | `int` | `60` | `EXPIRE` списка `reply:<id>` после каждого `RPUSH` |
| `dedup_ttl_s` | `float` | `600.0` | валидатор: больше `MAX_CALL_WINDOW_S` (120 с) |
| `max_call_s` | `float` | `70.0` | потолок одного вызова на стороне executor; валидатор: больше `CALL_TIMEOUT_S` (60 с) и не больше 120 с |
| `allowed_roots` | `list[str]` | `[]` → `%USERPROFILE%\Documents\Overseer` | см. «Разрешённые папки» |
| `max_conversations` | `int` | `4` | сколько разговоров одновременно держат книгу (замена `max_controllers`, см. «Книга на разговор») |
| `conversation_idle_ttl_s` | `float` | `1800.0` | через сколько простоя закрывается чистая книга разговора |
| `log_level` | `str` | `"INFO"` | |

**При `ENV=prod`** валидатор отклоняет `EXECUTOR_REDIS_URL` с пользователем `default` (в том числе
неявным) и с паролем `overseer` (`LOCAL_DEV_PASSWORD`). Вне prod пользователь `default` допустим, но
executor пишет `warning` `executor.unrestricted_redis_user`. Тексты ошибок адрес не повторяют.

На стороне api: `executor_pickup_timeout_s` (5) и `executor_call_budget_s` (70) — поля `Settings`
и ключи `.env.example`. Префикс у них тот же `EXECUTOR_`, но читает их api, а не executor:
`ExecutorSettings` таких полей не имеет и с `extra="ignore"` их пропускает.

**v1 поддерживает ровно один executor на один Redis.** Ключи без идентификатора машины, поэтому два
executor на одном Redis означали бы: оба читают одну очередь, и запрос пользователя А исполняется на
рабочем столе пользователя Б; heartbeat перезаписывают оба, и живой второй маскирует мёртвый первый;
`LREM` и дедупликация продолжают работать, но уже не про того адресата. Поэтому второй экземпляр
обязан отказаться стартовать (см. «Владение очередью» ниже). Несколько машин — это адресация
(`requests:<executor_id>`, выбор executor по разговору или пользователю) и отдельный тикет.

### Реализация (OVE-60)

Что из дизайна выше построено как есть, что изменилось по ходу и почему.

#### api: `RedisExecutorClient` (`libs/executor/redis_client.py`)

Шаги api из «Ключи и поток вызова» реализованы без изменений. Добавилось:

- **Свой пул соединений, а не общий `init_redis()`.** Блокирующий `BLPOP` держит соединение всё
  время ожидания (до 70 с), и в общем пуле он отнимал бы соединения у подтверждений и чата. Клиент
  строит отдельный `ConnectionPool` с `max_connections = 4`, а одновременные вызовы ограничивает
  `asyncio.Semaphore(4)`. Каждый вызов берёт **одно** соединение на весь свой путь (`Redis.client()`,
  single-connection): `GET heartbeat`, `RPUSH`, `BLPOP`, `LREM` идут по нему, и вызов не может
  застрять посреди обмена из-за пула. Пятый одновременный вызов ждёт места не дольше пикапа и
  получает `not_picked_up` (`reason=client_busy`) без постановки в очередь: executor исполняет
  вызовы по одному, и ждать за четырьмя другими бессмысленно.
- **Повторов нет и на уровне драйвера.** `Retry(NoBackoff(), 0)` задан явно: redis-py 6.x по
  умолчанию повторяет команду до трёх раз, а повтор `RPUSH` — это второй запрос. `socket_timeout` —
  самый длинный блок (5 с) плюс 5 с запаса, `socket_connect_timeout` — 2 с.
- **Обрыв после `RPUSH`** — `LREM`: снял — `transport_unavailable` (не выполнено), не снял —
  `transport_error` (неизвестно). Отмена хода до `accepted` — экранированный по времени `LREM`.
- **Ответ с чужим `id`** — `malformed_reply`, как и любой ответ вне контракта (лишнее поле на любом
  уровне, текст ошибки внутри `error`).
- **`deadline` уже прошёл до отправки** — `deadline_exceeded` без похода в Redis. Ожидание
  ограничено меньшим из `deadline` запроса и `executor_call_budget_s`.
- **В логах** — `request_id`, `conversation_id`, операция, код, исход, длительность и размер в
  байтах; аргументов, путей и значений ячеек нет (пришпилено тестом).

Подключение в `apps/api`: `init_executor_client(settings)` — первая строка внутри `try` в `lifespan`,
**после** проверок `LLM`-ключа и `API_TOKEN` и до `init_engine`: соединений он не открывает, а
неверные тайминги роняют старт до инфраструктуры. `close_executor_client()` — на выключении.
Зависимость — `ExecutorClientDep` в `apps/api/deps.py`; инструменты, у которых нет DI, берут
`get_executor_client()` по имени модуля, тем же приёмом, что реестр и браузер.

#### executor: владение очередью и heartbeat (`apps/executor/lease.py`)

**Ключ владения отделён от heartbeat** — `overseer:executor:owner` (значение — `instance_id`) рядом с
`overseer:executor:heartbeat`. Дизайн предлагал сравнивать `instance_id` внутри JSON heartbeat, но
тогда Lua-скрипту пришлось бы разбирать JSON (`cjson`) ради одного поля. Оба ключа пишутся вместе,
одним скриптом и с одним TTL:

| Скрипт | Что делает |
|---|---|
| захват | `SET owner <id> NX PX ttl`; удалось — `SET heartbeat <json> PX ttl` |
| продление | `GET owner == <id>` → переписать оба ключа с новым `sent_at`; иначе `0` |
| освобождение | `GET owner == <id>` → `DEL owner heartbeat`; иначе ничего |

Скрипты идут через `EVAL` (не `EVALSHA`/`SCRIPT LOAD`): ACL-пользователю executor тогда не нужны
команды управления скриптами.

- **Heartbeat значит «процесс и его цикл событий живы»**, а не «Excel отвечает». Его продлевает
  отдельная задача на event loop, а COM-вызовы идут на STA-потоке, поэтому heartbeat не замирает на
  долгом вызове (пришпилено тестом). Зависший COM-вызов ограничен не heartbeat, а
  `CALL_TIMEOUT_S` контроллера (60 с) и `max_call_s` executor (70 с).
- **Подтверждённое время.** Каждое успешное продление даёт `confirmed_for = ttl − interval`
  (10 с) от момента отправки. Цикл приёма делает `BLPOP` только внутри этого окна и блокирует не
  дольше остатка: если Redis пропал, executor перестаёт брать запросы раньше, чем его владение
  могло бы истечь и достаться другому.
- **Потеря владения** (скрипт продления вернул `0`: ключ истёк или его занял другой) — приём
  останавливается, текущий вызов доигрывается, чужой ключ не трогается, процесс выходит с кодом 1
  (`OwnershipLostError`). Сетевые сбои продления — только `warning`, не потеря.
- **Второй экземпляр.** Захват не удался — executor читает heartbeat и ждёт: изменился `sent_at`
  (владелец жив и продлевает) — отказ сразу (`ExecutorAlreadyRunningError`, код 1, текст про
  второй экземпляр); ключ истёк — захват. Ждать дольше `ttl + interval` не приходится.
- **Перезапуск сразу после падения.** Упавший executor оставляет владение до TTL (≤ 15 с), и новый
  стартует, как только оно истечёт: замер — 14,5 с после `SIGKILL`. Разделить «упал» и «жив, но
  молчит» быстрее нельзя, не поверив процессу, который мог не умереть, поэтому выбран честный
  таймаут, а не принудительный захват.

#### executor: цикл приёма (`apps/executor/consumer.py`)

Шаги executor из дизайна реализованы как есть, с уточнениями:

- `BLPOP` с таймаутом 1 с (и не дольше подтверждённого времени), между вызовами — проверка флага
  остановки и потери владения. Отмена посреди `BLPOP` не используется для остановки: так снятый с
  очереди запрос не может потеряться на выходе.
- **Один запрос за раз**, порядок — FIFO списка (пришпилено тестом на перекрытие).
- **Ошибка в одном запросе цикл не роняет**: `logger.exception("executor.serve_failed")`, дальше
  следующий. Исключение обработчика — `internal_error` в ответе и полный трейсбек в локальном логе.
  Исключения `Office*` — свой код через `error_code_for()`, `RequestRefusedError` (сюда относится
  отказ по пути) — свой код, превышение `max_call_s` — `timeout` (отличается от `TimeoutError`
  изнутри обработчика по `scope.expired()`). `CancelledError` проходит насквозь; если отменили
  посреди вызова, executor успевает ответить `internal_error`, чтобы api не ждал вслепую.
- **Ответы** — `RPUSH` и `EXPIRE reply_ttl_s` одним конвейером без `MULTI` (ACL не нужен
  `MULTI/EXEC`). Ответ сверх `MAX_REPLY_BYTES` заменяется на `internal_error`.
- **Диспетчеризация** — `ExecutorDispatcher.dispatch()` (`apps/executor/dispatch.py`): `match` по
  классу модели запроса и `assert_never` для остального, то есть mypy требует покрыть каждый член
  объединения `ExecutorRequest`. Ни `getattr`, ни имён методов с провода (тест разбирает AST
  модуля). Heartbeat объявляет `dispatcher.operations`. Место для Word: `WordOperations` рядом с
  `ExcelOperations` и три `case` в том же `match`, когда OVE-30/31 добавят модели запросов в
  контракт.

**Остановка.** `SIGINT`/`SIGTERM` (POSIX) — `request_stop()`: приём прекращается, вызов в работе
доигрывается (в пределах `max_call_s`), затем `release()` снимает владение и heartbeat (api сразу
видит `executor_unavailable`), затем Excel закрывается через финализацию контроллера. На Windows
`add_signal_handler` нет: первый Ctrl+C asyncio превращает в отмену главной задачи, сервис ловит её,
делает ту же мягкую остановку и только потом пробрасывает отмену; второй Ctrl+C — жёсткий выход.

#### Разрешённые папки (`apps/executor/paths.py`)

`PathPolicy.check()` — внешний слой поверх `validate_workbook_path()` контроллера. Отказ —
`PathNotAllowedError` (код `path_not_allowed`), пути в тексте и в логе нет. Порядок:

1. **Строковые правила на `PureWindowsPath`** (работают на любой ОС, гоняются в CI). Отклоняются:
   UNC (`\\server\share`, `//server/share`), device- и extended-пути (`\\.\`, `\\?\`,
   `\\?\UNC\`, `\??\`), пути без буквы диска или относительно диска (`C:x`, `\x`, `x`),
   компоненты `..`, двоеточие вне буквы диска (альтернативные потоки `file.xlsx:s`, `::$DATA`),
   `< > " | ? *` и управляющие символы, компоненты с точкой или пробелом в конце (Windows их
   отрезает и путь меняет смысл), зарезервированные имена устройств в любом компоненте и с любым
   расширением (`CON`, `PRN`, `AUX`, `NUL`, `COM1–9`, `LPT1–9`, `COM¹²³`, `LPT¹²³`, `CONIN$`,
   `CONOUT$`, `CLOCK$`).
2. **Проверка контроллера** — абсолютный путь, расширение книги, длина (их ошибки остаются
   `invalid_input`).
3. **Вхождение в разрешённую папку** — без учёта регистра, строго внутри (сама папка и соседняя
   `OverseerEvil` не подходят).
4. **На Windows — то же после разрешения ссылок**: `os.path.realpath()` раскрывает симлинки и
   junction'ы, ответ с `\\?\UNC\` отклоняется, `\\?\` снимается, и путь снова проверяется против
   **так же разрешённых** корней (корень сам может быть junction'ом, например на перенаправленные
   «Документы»).

**Безопасный дефолт** — одна выделенная папка `%USERPROFILE%\Documents\Overseer`, которую executor
создаёт при старте, а не весь профиль: агенту не нужен доступ к остальным документам, а пользователю
видно, куда он пишет. Корни из `EXECUTOR_ALLOWED_ROOTS` проходят те же строковые правила при чтении
настроек и обязаны существовать на старте (опечатка — отказ запуститься, а не «ничего не разрешено»).
`USERPROFILE` не задан или сетевой — отказ запуститься с просьбой задать папки явно.

Не закрыто: окно между проверкой и `Workbooks.Open`/`SaveAs` (junction, подменённый в этот момент);
короткие имена 8.3 сравниваются строкой и при несовпадении просто отклоняются; разрешение ссылок,
регистр на реальной ФС и junction'ы на Windows не проверялись — тесты есть
(`tests/integration/test_executor_paths_windows.py`, `@pytest.mark.windows`).

#### Книга на разговор (`apps/executor/excel/sessions.py`)

`ExcelController` держал одну книгу на всех, и два разговора писали бы в книги друг друга. Выбран
**один процесс Excel и своя книга на каждый разговор**: контроллер хранит `{conversation_id: книга}`,
а `ConversationWorkbooks` над ним ведёт простой и потолок. Процесс Excel на разговор отклонён:
каждый — секунды старта и сотни мегабайт, свой STA-поток и своя финализация, а изоляции, которой нет
у книг внутри одного экземпляра, он не добавляет: книги одного экземпляра друг друга не видят, если
их не связывать формулами, а формулы по умолчанию пишутся текстом.

- **Поиск книги** — по `conversation_id` запроса. Разговор без своей книги получает «нет открытой
  книги», а не чужую.
- **Одно имя файла — один разговор.** Excel не держит в одном экземпляре две книги с одинаковым
  именем файла, даже в разных папках, а открытие того же пути вернуло бы ту же книгу. Поэтому
  открытие или «сохранить как» с именем, которое уже занято книгой другого разговора, — сразу
  `OfficeFileLockedError` (`file_locked`), до COM.
- **Простой** (`conversation_idle_ttl_s`): сборщик идёт на простое цикла приёма, не чаще раза в
  30 с, и закрывает только **чистые** книги. Книга с несохранёнными изменениями остаётся открытой и
  попадает в лог один раз (`excel.unsaved_workbook_kept`). Она не сохраняется автоматически и не
  выбрасывается; закроется, когда разговор её сохранит.
- **Потолок** (`max_conversations`): новому разговору место освобождает самая давняя чистая книга
  другого разговора. Тот, придя снова, получит «нет открытой книги» и откроет её заново — данные не
  теряются. Если чистых нет, новый разговор получает `OfficeBusyError` (`busy`): лучше отказать,
  чем закрыть чужую работу. Текст для модели у `busy` общий («Office занято»); отдельного кода под
  этот случай в контракте нет.
- **Остановка** — пункт 6 правила «не трогай Excel пользователя»: несохранённые книги не
  закрываются, экземпляр передаётся пользователю.

#### ACL-пользователь Redis `overseer-executor`

Правила лежат в `docker/redis/executor.acl`; это единственный их источник и для compose, и для теста:

```text
resetchannels -@all
+ping +select +client|setinfo
+blpop ~overseer:executor:requests
(+rpush +expire ~overseer:executor:reply:*)
(+get +set +del +eval ~overseer:executor:heartbeat ~overseer:executor:owner ~overseer:executor:seen:*)
```

Селекторы Redis 7 разводят «какие команды» и «к каким ключам»: к очереди запросов у executor есть
только `BLPOP`, поэтому писать в неё (`RPUSH`/`LPUSH`/`LREM`/`DEL`) он не может — подделать запрос
самому себе нельзя. `RPUSH` и `EXPIRE` разрешены только на `reply:*`, `GET/SET/DEL/EVAL` — только
на своих ключах состояния. Команды внутри `EVAL` проверяются по тем же правилам: скрипт не дотянется
ни до ключа вне пространства, ни до `RPUSH` в очередь. Ни ключей подтверждений, ни Arq, ни данных
диалогов, ни `KEYS`/`SCAN`, `ACL`, `CONFIG`, `FLUSH*`, `INFO`, `CLIENT LIST/KILL`, pub/sub,
`EVALSHA`, `SCRIPT`, `FUNCTION`/`FCALL`, `SHUTDOWN`, `MONITOR`, `REPLICAOF`, `MODULE`. Синтаксис
проверен на живом Redis 7.4.11 тестом, а не по документации: в нём же — полный вызов от этого
пользователя и `ACL DRYRUN` для команд, которые нельзя пробовать по-настоящему. Остаточный риск:
`EVAL` позволяет executor занять сервер долгим скриптом (до `lua-time-limit`). Это локальный процесс
того же пользователя, так что такой отказ в обслуживании принят.

**Провижининг в compose.** `docker/redis/entrypoint.sh` смонтирован в контейнер вместе с правилами,
собирает конфиг (`requirepass` для `default` и, если задан `REDIS_EXECUTOR_PASSWORD`, строку
`user overseer-executor reset on >… <правила>`) и отдаёт его `redis-server -` через stdin. Задание
просило ACL-файл, но выбран конфиг через stdin: так пароль не попадает ни в командную строку, ни
на диск контейнера, а директива `user` в основном конфиге совместима с `requirepass` (с `aclfile`
`requirepass` игнорируется). Проверено на живом контейнере: процесс идёт от `redis`, в `ps` и
`docker inspect .Args` пароля нет, `ACL LIST` показывает селекторы, `default` по-прежнему
`PONG`-ует в healthcheck. Пользователь **необязателен**: пустой `REDIS_EXECUTOR_PASSWORD` (дефолт
compose `${REDIS_EXECUTOR_PASSWORD:-}`) — строки `user` нет, всё как до OVE-60. Значения по
умолчанию у пароля нет нигде. Скрипт отказывается запускать Redis, если пароль короче 32 символов,
содержит что-то кроме `A-Z a-z 0-9 . _ ~ -` (пробел или перевод строки иначе дописали бы правила
в конфиг) или совпадает с `REDIS_PASSWORD`; значение в сообщении не повторяется. Переменные
окружения контейнера по-прежнему видны в `docker inspect` — как и `REDIS_PASSWORD` с OVE-59.

**Секреты в логах.** `redact_secrets()` (`libs/core/logging.py`) теперь заменяет на `***` пароль в
`redis://user:<…>@`, значения `REDIS_PASSWORD=`/`REDIS_EXECUTOR_PASSWORD=` и `>пароль` в ACL-строке,
а процессор `redact_event_secrets` применяет то же к строковым полям событий `structlog` (в том
числе к трейсбеку после `format_exc_info`). `RedisTarget` для логов executor несёт хост, порт и
пользователя, без пароля.

#### Как запустить

1. В `.env`: `REDIS_EXECUTOR_PASSWORD=<openssl rand -hex 32>` и
   `EXECUTOR_REDIS_URL=redis://overseer-executor:<тот же пароль>@127.0.0.1:56379/0`.
2. Пересоздать Redis, чтобы он завёл пользователя: `docker compose -f docker/docker-compose.yml up -d
   --force-recreate redis` (переменные должны дойти до compose — тем же способом, что
   `REDIS_PASSWORD`).
3. На Windows: `uv sync --group executor`, затем `uv run python -m apps.executor.main`.

#### Замеры

Compose Redis 7.4.11 на macOS, executor — отдельный процесс от пользователя `overseer-executor` с
фейковым диспетчером, api — `RedisExecutorClient.from_settings()` с боевыми таймингами (пикап 5 с,
срез 5 с, TTL 15 с, интервал 5 с):

| Ситуация | Оценка OVE-29 | Замер |
|---|---|---|
| executor не запущен → `executor_unavailable` | миллисекунды | медиана 0,6–0,7 мс, максимум 3,8 мс (n = 30) |
| полный круг до executor и обратно | — | медиана 2,2 мс, p95 3,2–3,6 мс (n = 30) |
| executor занят 8-секундным вызовом → `not_picked_up` | 5 с | 5,02–5,04 с |
| `SIGKILL` посреди вызова → `reply_timeout` | ≈ 20 с | 14,2 с после убийства (TTL остатка + срез) |
| перезапуск сразу после `SIGKILL` | ≤ 15 с | 14,5 с (остаток владения был 14,0 с) |
| второй executor при живом первом | отказ старта | код 1 через 4,7 с, текст про второй экземпляр, пароля в выводе нет |
| `SIGTERM` | — | выход 0, ключей владения не осталось, следующий вызов — `executor_unavailable` за 1–1,6 мс |
| захват владения на старте | — | 54–55 мс |

Это loopback на одной машине без Docker Desktop под Windows: задержки сети там будут другими, а
ограничения по времени (пикап, TTL, срезы) от сети не зависят.

### Что проверено и что нет

**Проверено:** привязка и аутентификация Redis на поднятом контейнере (таблица в начале раздела);
весь контракт — юнит-тестами (`tests/unit/test_executor_contract.py`); с OVE-60 — клиент api на
живом Redis (`tests/integration/test_executor_redis_client.py`: быстрый отказ без heartbeat с
измеренным потолком, снятие невзятого запроса, гонка `LREM` против `BLPOP` в обоих исходах через
барьер, смерть и перезапуск executor посреди вызова, бюджет, версия и операции heartbeat, ответы
вне контракта, слишком большой запрос, недоступный Redis, отмена, потолок одновременных вызовов,
порядок, отсутствие данных в логах); executor на живом Redis
(`tests/integration/test_executor_consumer.py`); изоляция ACL на живом Redis 7
(`tests/integration/test_executor_redis_acl.py`); правила путей, книга на разговор, настройки,
сборка конфига Redis и маскировка секретов — юнит-тестами; замеры выше.

**Не проверено (нужна Windows):** что Windows-процесс достаёт до `127.0.0.1`, опубликованного Docker
Desktop; `redis-py` на `ProactorEventLoop`; мягкая остановка по Ctrl+C на Windows; разрешение
junction'ов и симлинков, регистр на реальной ФС; живой Excel целиком, включая передачу экземпляра с
несохранёнными книгами при остановке.
